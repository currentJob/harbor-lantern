## 1. 문제 정의

### 1.1 배경

사용자는 이미 홍콩 3박4일(10.5 월 → 10.8 목) 일정을 담은 **단일 정적 HTML 페이지**를 가지고 있다.
이 페이지는 관광 가이드로서 완성도가 높다 — 다크 네온 테마, Leaflet 다크 타일 지도, 일자별 탭,
카드 펼침, 진행률 링, 홍콩 현지시각 시계, `watchPosition` 기반 실시간 위치 추적과 거리 표시,
구글맵 길찾기 딥링크, 모바일 우선 레이아웃(max-width 560px), `prefers-reduced-motion` 대응까지 갖췄다.

문제는 **여행이 계획대로 흘러가지 않는다는 것**과 **혼자 가는 여행이 아니라는 것**이다.
현재 페이지는 두 상황 모두를 다루지 못한다.

### 1.2 참조 페이지의 실제 한계

아래는 일반론이 아니라 `reference/original-static-page.html`을 읽어 확인한 사실이다.

| # | 문제 | 참조 페이지의 현재 구현 | 목표 상태 |
|---|------|------------------------|-----------|
| P1 | **일정 데이터가 코드에 박혀 있다** | `<script>` 안의 `const DAYS = [...]` 배열(4일 · 총 27스팟). 스팟 추가·삭제·시간 변경을 하려면 HTML 파일 본문을 편집해야 한다 | 서버 DB에 저장하고 화면에서 CRUD |
| P2 | **완료 체크가 기기 1대에 갇힌다** | `store.set("hk_done", done)` — `localStorage` 키 `hk_done`. 다른 기기·다른 동행에게는 보이지 않고, 브라우저 데이터를 지우면 사라진다 | 서버에 저장하고 동행 전원이 같은 상태를 본다 |
| P3 | **동행과 공유할 방법이 없다** | 공유 수단은 HTML 파일 자체를 보내는 것뿐. 각자 받은 파일은 각자의 `localStorage`로 갈라진다 | 여행마다 발급되는 초대코드로 같은 데이터에 참여 |
| P4 | **순서를 바꿀 수 없다** | 카드 순서는 `DAYS[di].spots` 배열 순서 고정. 비가 오거나 줄이 길어 순서를 바꾸면 화면과 현실이 어긋난다 | 드래그/버튼으로 순서 변경, 일자 간 이동 지원 |
| P5 | **돈 이야기를 담을 곳이 없다** | 경비 관련 기능 전무 | 지출 기록 + 동행 정산(최소 송금) |
| P6 | **거리는 알지만 시간은 모른다** | `dist()`는 하버사인 직선거리만 계산(`fmt()`로 m/km 표기). 다음 스팟까지 몇 분 걸리는지, 하루 총 이동이 얼마인지는 알 수 없다 | 서버가 구간 이동시간·총 거리 계산 |
| P7 | **영업시간이 텍스트일 뿐 경고하지 않는다** | `hours:"매일 08:00–18:00"`, `closed:"일부 갤러리 월요일"` 같은 자유 문자열을 그대로 출력만 한다. 18시에 도착할 예정이어도 아무 경고가 없다 | 도착 예상시각 기준 닫힘/휴무 경고 |
| P8 | **고정시각 일정과의 충돌을 못 잡는다** | `{t:"20:00", n:"심포니 오브 라이트"}`는 매일 20:00 시작 고정인데, 앞 스팟이 늦어져도 화면은 조용하다 | 고정시각 일정 침범을 충돌로 검출 |
| P9 | **날씨·환율 정보가 없다** | 팁 목록에 "10월 날씨는 덥고 습함(~28℃)"라는 정적 문장만 있다 | 서버가 캐시한 날씨·환율 제공 |
| P10 | **외부 CDN에 의존한다** | Leaflet CSS/JS를 `cdnjs.cloudflare.com`에서 로드. 네트워크가 나쁘면 지도가 통째로 안 뜨고, 자동 테스트도 네트워크에 묶인다 | 프론트 자산 로컬 벤더링 |
| P11 | **써 둔 27곳 밖은 아무것도 모른다** | 앱이 아는 장소는 `DAYS` 배열에 적힌 27개가 전부다. 지금 서 있는 자리 근처에 뭐가 있는지 물어볼 방법이 없어, 배가 고파지면 앱을 닫고 다른 지도 앱을 켜야 한다 | 현재 위치 기준 근처 장소를 그 자리에서 조회하고 일정에 넣는다 |
| P12 | **가까운 곳은 알아도 좋은 곳은 모른다** | 근처 검색(REQ-017)은 OpenStreetMap 데이터라 **평점·후기가 없다.** 반경 안의 식당을 거리순으로 늘어놓을 뿐이라, 그중 어디가 좋은지는 여전히 앱 밖에서 찾아야 한다. 무료로 리뷰를 가져올 API 도 없다(설계서 §6.23 조사 결과) | 평가가 검증된 목록을 **미리 조사해 저장소에 넣고**, 출처와 한계를 함께 보여 준다 |

### 1.3 대상 사용자

계정·비밀번호 개념이 없으므로 역할은 **여행 참가자 한 종류**다.

- **여행 개설자(Organizer)**: 여행을 만들고 초대코드를 동행에게 전달한다. 별도 권한 등급은 두지 않는다(가정 A4).
- **동행 참가자(Companion)**: 초대코드로 참여해 표시명을 정하고, 같은 일정·체크·경비를 읽고 쓴다.
- **현장 사용자(On-the-ground)**: 위 둘과 동일 인물이지만 홍콩 현지에서 모바일로 쓰는 상태. 위치 추적·거리·길찾기·영업시간 경고가 이 맥락의 기능이다.

| MVP 4대 기능(편집·정산·동선·경고)이 각각 자동 테스트로 검증됨 | AC-006~AC-025 |

## 2. 범위

### 2.1 MoSCoW

| 구분 | 항목 |
|------|------|
| **Must (이번 릴리스)** | 여행 생성 + 27스팟 시드 주입 · 초대코드 발급/참여(무계정) · 스팟 CRUD · 순서 변경 및 일자 간 이동 · 방문 완료 체크 서버 공유 · 경비 기록 · 최소 송금 정산 · 동선 최적화 · 구간 이동시간/총 거리 서버 계산 · 영업시간 경고 · 일정 충돌 검사 · 날씨/환율 캐시 연동 및 폴백 · 기존 UX 자산 유지(다크 네온·Leaflet 지도·일자 탭·진행률 링·홍콩 시계) · 실시간 위치/거리/가까운 순 정렬/구글맵 딥링크 · 폴링 동기화 · MIT LICENSE + CI 게이트 · **현재 위치 기준 근처 음식점·카페 조회(OSM) 및 일정 추가 — v1.1 승격** · **미쉐린 홍콩·마카오 큐레이션 목록 — v1.2 추가** |
| **Should (MVP 제외 — 다음 릴리스 후보)** | 여행 기간·날짜 자유 편집(시작일만 Must) · 일정/경비 CSV·JSON 내보내기 · 참가자별 색상·아바타 · 스팟 메모/코멘트 스레드 · 경비 카테고리 통계 · 초대코드 재발급/폐기 · 되돌리기(undo) |
| **Could (MVP 제외)** | 사진 업로드·갤러리 · 다국어(en/zh-HK) · 라이트 테마 토글 · 예산 상한 알림 · 여행 종료 후 요약 리포트 |
| **Won't (이번 릴리스에서 만들지 않음)** | 계정/비밀번호/소셜 로그인 · WebSocket 실시간 푸시(폴링으로 대체) · **실제 대중교통 경로탐색(MTR/버스 API 연동)** — 이동시간은 거리 기반 결정론 모델로 근사(가정 A8) · PWA 오프라인 캐시·오프라인 지도 타일 · 네이티브 iOS/Android 앱 · 실제 송금/결제 연동(정산은 "누가 누구에게 얼마" 계산까지) · 다중 여행 대시보드 · 푸시 알림 · 관리자 백오피스 |

**Should·Could에 놓인 항목은 MVP 산출물에 포함하지 않는다.** 구현 단계에서 여유가 생겨도 착수하지 않으며, 필요하면 다음 릴리스에서 요구사항으로 승격한다(과대범위는 빌드 실패의 최대 원인이다).

### 2.2 범위 축소 근거

원 컨셉("동적 여행 가이드")은 여행 앱 전반으로 무한 확장 가능하다. 1차 릴리스를 위 Must로 자른 근거:

1. **P1~P4(편집·공유)를 해결하지 못하면 나머지 기능이 무의미하다.** 데이터를 못 고치는 앱에 정산을 붙여도 쓰이지 않는다.
2. **MVP 4대 기능은 서로를 강화한다.** 순서 변경(P4) → 이동시간 재계산(P6) → 도착 예상시각 변화 → 영업시간 경고·충돌 검사(P7·P8). 하나의 계산 파이프라인으로 묶인다.
3. **외부 연동을 날씨·환율 둘로 제한**했다. 경로탐색 API까지 넣으면 결정론 테스트 원칙(NFR-003)을 지키기 위한 목킹 표면이 급격히 커진다.

> **v1.1 개정(2026-09-14).** "스팟 검색·외부 POI 추천"을 Could에서 **Must로 승격**했다(REQ-017·REQ-018).
> 사용자가 실제로 써 보고 요청한 것이며, 근거가 되는 한계는 P11이다 — 앱이 아는 장소가 27개뿐이라
> 배가 고파지면 앱을 닫게 된다. 외부 연동이 셋으로 늘지만 **공급자 포트·TTL 캐시·stale 폴백이라는
> 기존 패턴을 그대로 재사용**하므로 목킹 표면은 어댑터 하나만큼만 커진다(위 3번의 우려가 실제로
> 문제가 되는 것은 경로탐색처럼 계산 결과가 응답에 종속될 때이지, 조회 결과를 그대로 보여 줄 때가 아니다).
> 경로탐색은 여전히 Won't이다.

### 2.3 명시적 가정

| # | 가정 | 근거 |
|---|------|------|
| A1 | 시드 영업시간·휴무는 참조 HTML의 값을 그대로 옮긴 **근사치**이며 정확성을 보증하지 않는다. 그래서 "사용자가 편집할 수 있다"가 요구사항(REQ-003)이 된다 | 참조 HTML 자체가 "영업시간은 근사치입니다. 방문 직전 각 명소 공식 채널로 재확인하세요"라고 명시. 웹 재조사로 대체하지 않는다 |
| A2 | 여행 기본 기간은 시드 라벨과 동일한 **2026-10-05(월) ~ 2026-10-08(목)**, 시작일은 여행 생성 시 지정 가능(기본값 2026-10-05) | 참조 HTML의 `pickDay()`가 10/5~10/8을 Day 1~4에 매핑 |
| A3 | 기본 통화는 **HKD**, 보조 표시 통화는 **KRW**. 금액은 부동소수가 아닌 정수 minor unit(HKD cent)으로 저장 | 정산 오차 방지(NFR-014) |
| A4 | **초대코드를 아는 사람 = 전체 편집 권한.** 권한 등급·소유자 개념을 두지 않는다. 보안 경계는 코드의 추측 난이도(NFR-005)와 시도 제한(NFR-006)뿐이며, 이 사실을 UI에 명시한다 | 무계정 공유 모델의 필연적 귀결. 사용자 확정 사항 |
| A5 | 동시 편집은 **낙관적 잠금**으로 처리한다(리소스 version 불일치 시 409 + 최신 상태 반환). 자동 병합은 하지 않는다 | 동행 2~5명 규모에서 충돌 빈도가 낮고, 자동 병합은 검증 비용이 크다 |
| A6 | 단일 인스턴스 SQLite 배포를 전제한다. 수평 확장·복제는 범위 밖 | 사용자 확정 스택 |
| A7 | 날씨·환율 공급자는 Phase 2(설계)가 선정한다. 요구사항은 "주기 캐시 + 마지막 캐시 폴백 + 목킹 가능한 포트"까지 규정한다 | 공급자 선택은 설계 결정. 시점 의존 정보이므로 Phase 2가 웹으로 실물 확인 후 버전·엔드포인트 고정 |
| A8 | 이동시간은 실제 경로탐색이 아니라 **거리 기반 결정론 모델**(직선거리 × 우회계수 ÷ 모드별 평균속도 + 고정 환승 여유)로 근사하며, 계수는 설정값으로 노출하고 화면에 "추정치"로 표기한다 | Won't에서 경로탐색 API를 제외한 결과. 계수 기본값은 Phase 2가 정한다(열린 결정 O2) |
| A9 | 시간대는 **홍콩 표준시(HKT, UTC+8, 서머타임 없음)** 고정. 저장은 UTC, 표시·계산은 `Asia/Hong_Kong` | 참조 HTML도 `timeZone:'Asia/Hong_Kong'` 사용. 시점 의존 사실이 아닌 안정 상수이므로 웹 재확인 대상 아님 |

## 8. 지역 여행 확장 요구사항 (2026-09-14)

| ID | 요구사항 | 인수 기준 |
|---|---|---|
| REQ-019 | 메인에서 나라·지역을 검색하고 도시·동네 및 여행 날짜를 선택한다. 홍콩 가이드는 별도 진입한다. | AC-058 |
| REQ-020 | 현지 날짜·요일·공개 영업시간과 이동거리에 기반한 추천 동선을 생성하고 최근 여행을 브라우저에 보관한다. | AC-059 |
| REQ-021 | 현재 위치 또는 선택 여행지 주변 음식점과 제공되는 영업시간·평점·후기·메뉴 링크를 표시한다. | AC-060, AC-061 |

| AC | 인수 기준 |
|---|---|
| AC-058 | 1~14일 범위만 허용하고 시작일 이전 종료일·범위 밖 좌표를 거부한다. |
| AC-059 | 주간 휴무일에 확정 방문을 넣지 않으며 전체 체류가 영업시간 안에 들어간다. 같은 장소를 반복하지 않는다. 미확인 영업시간을 명시한다. |
| AC-060 | 위치 기준 거리·반경을 적용하고 API 키 없는 결과에 평점·후기를 만들어 넣지 않는다. |
| AC-061 | Google 연결 시 평점·평가 수와 후기 작성자·원문 링크를 유지하며 서버 키를 프런트에 보내지 않는다. 실제 연결 검증은 키 설정 후 별도 수행한다. |

업체별 추천 메뉴는 실제 데이터가 있을 때만 표시한다. 현재 공개 데이터에 없는 메뉴는 미제공이다.
국가 간 이동·항공·숙박·실제 대중교통 최단 경로는 이번 동네 단위 추천 범위에 포함하지 않는다.
