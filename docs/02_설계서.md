## 1. 설계 요약

01 문서가 정의한 것은 "정적 HTML 한 장을 서버 기반 공유 가이드로 바꾼다"이다. 설계는 그것을
**하나의 파이썬 프로세스**로 구현한다 — FastAPI가 API와 정적 프론트를 함께 서빙하고, SQLite 파일
하나가 영속을 맡으며, 프론트는 빌드 체인 없이 브라우저가 바로 읽는 ES 모듈이다.

이 구조를 고른 이유는 셋이다.

1. **REQ-001~016의 계산 파이프라인이 하나다.** 순서 변경(REQ-005) → 이동시간(REQ-010) →
   도착 예상시각(REQ-011) → 영업시간 경고(REQ-012) → 충돌(REQ-013)이 한 함수 사슬로 이어진다.
   이 사슬을 서비스 경계로 쪼개면 얻을 것 없이 왕복만 는다.
2. **NFR-003(결정론 테스트)이 프로세스 경계를 싫어한다.** 외부 호출은 포트 2개(날씨·환율)뿐이고,
   그 둘만 어댑터로 뽑아내면 나머지 전부가 인프로세스 테스트 대상이 된다.
3. **NFR-001이 빌드 체인을 금지한다.** 번들러가 없으므로 프론트를 별도 서버로 띄울 이유도 없다.
   FastAPI의 `StaticFiles`가 그대로 배포 단위가 된다.

## 2. 아키텍처

### 2.1 컴포넌트 분해 & 기술 선택 (DSN-01)

배포 단위는 하나지만 책임은 넷으로 나뉜다. 스택은 C1(사용자 확정)으로 고정돼 있으므로,
설계의 몫은 "왜 이 배치가 요구를 만족하는가"와 "대안의 대가는 무엇인가"를 남기는 것이다.

| 컴포넌트 | 책임 (하는 것 / 안 하는 것) | 스택 · 근거 | 원커맨드 |
|---------|---------------------------|------------|---------|
| `domain` | 순수 계산 — 거리·이동시간·타임라인·영업시간·경고·충돌·최적화·금액·정산·초대코드. **I/O 없음. DB·HTTP·시각 조회 안 함** | 표준 라이브러리 Python만. 외부 의존 0 → 단위 테스트가 밀리초 단위로 끝나고 NFR-003을 구조적으로 만족 | `uv run pytest tests/domain -q` |
| `storage` | SQLite 연결·PRAGMA·트랜잭션·리포지토리·시드 주입. **비즈니스 판단 안 함** | 표준 라이브러리 `sqlite3`. **ORM 미도입** — 아래 §3.3 | — |
| `services` + `api` | 유스케이스 조립, HTTP 표면, 인증(참가자 토큰), 레이트 리밋, 외부 어댑터 | FastAPI + Pydantic. OpenAPI를 프레임워크가 생성하므로 `contracts/openapi.yaml`과의 드리프트를 테스트로 잡을 수 있다 | `uv run python -m harbor_lantern` |
| `web` | 브라우저 UI — 다크 네온 테마, Leaflet 지도, 탭·카드·진행률 링·시계·위치추적·거리정렬 | 바닐라 JS(ES 모듈) + 로컬 벤더링 Leaflet. 번들러 없음(NFR-001), CDN 없음(NFR-015) | FastAPI가 `/`로 서빙 |

**단일 프로세스인 이유**: A6이 단일 인스턴스 SQLite를 전제한다. 프로세스를 쪼개면 SQLite 파일을
공유해야 하고, 그 순간 WAL의 "다중 리더 + 단일 라이터" 보장을 프로세스 간 경합으로 밀어 넣는다.
얻는 것이 없다.

**대안과 대가**

| 대안 | 대가 |
|------|------|
| 프론트를 별도 정적 서버(nginx/Vite dev)로 분리 | 개발자가 두 프로세스를 띄워야 하고 CORS 설정이 생긴다. NFR-001이 빌드 체인을 금지해 얻는 이득(HMR·번들 최적화)도 없다 |
| 도메인 계산을 별도 워커/큐로 | 27스팟 규모에서 계산은 밀리초 단위다(§8 목표치). 큐는 지연과 운영 표면만 늘린다 |
| WebSocket 실시간 푸시 | 01의 Won't. 폴링 + ETag로 대체(DSN-21) |

### 2.2 의존 방향과 포트/어댑터 (DSN-02)

```
            ┌──────────────────────────────────────────┐
  브라우저 ─▶│ api/          FastAPI 라우트 · 스키마 · 인증 │
            ├──────────────────────────────────────────┤
            │ services/     유스케이스 조립 · 트랜잭션 경계 │
            ├───────────────┬──────────────────────────┤
            │ domain/       │ storage/                 │
            │ 순수 계산      │ sqlite3 리포지토리          │
            └───────────────┴──────────────────────────┘
                            │
                    ports.py │ (Protocol)
                            ▼
             ┌──────────────────────────────┐
             │ WeatherPort · FxPort          │
             │  ├ openmeteo.py  (실제 HTTP)   │
             │  ├ frankfurter.py(실제 HTTP)   │
             │  └ tests/fakes  (호출 카운터)   │
             └──────────────────────────────┘
```

**규칙 (구현 중 지켜야 하는 것)**

- `domain/`은 `storage/`·`api/`·`httpx`·`datetime.now()`를 **import 하지 않는다.** 위반 시
  `tests/test_layering.py`가 실패한다(import 그래프 정적 검사).
- 아웃바운드 HTTP는 `services/external/` 안에서만 일어난다. 다른 곳에 `httpx`가 나타나면 테스트 실패.
- 어댑터는 `Protocol`로 정의된 포트를 만족하기만 하면 되므로, 테스트는 **호출 횟수를 세는 가짜**를
  꽂는다(AC-026의 "호출 횟수 0/1"을 세려면 가짜가 카운터를 들고 있어야 한다).

### 2.3 시계 포트 (DSN-03)

`Clock`은 `now_utc() -> datetime`(tz-aware, UTC) 하나만 갖는 `Protocol`이다. 구현은 둘:
`SystemClock`(운영)과 `FixedClock(instant)`(테스트, `advance()` 지원). FastAPI 의존성으로 주입하고,
`domain/`은 시계를 **받지 않는다** — 필요한 시각은 인자로 들어온다.

**HKT 변환은 `zoneinfo`를 쓰지 않는다.** A9가 확정한 대로 홍콩은 UTC+8 고정·DST 없음이므로
`HKT = timezone(timedelta(hours=8))` 상수로 충분하다. `zoneinfo.ZoneInfo("Asia/Hong_Kong")`은
Windows에서 `tzdata` 패키지를 추가로 요구하는데, 고정 오프셋 지역에 의존성을 하나 더 다는 것은
대가가 이득보다 크다. 프론트의 시계 표시(AC-031)는 참조 HTML과 동일하게 브라우저의
`toLocaleTimeString(..., {timeZone:'Asia/Hong_Kong'})`을 쓰되, **검증 대상 함수는 오프셋 상수를
쓰는 순수 함수**(`formatHkt(utcMillis)`)로 분리해 고정 입력에 고정 출력을 낸다.

### 3.2 동기 서버로 간다 (핸들러 = `def`)

FastAPI는 `def` 핸들러를 스레드풀에서 돌린다. 그래서 블로킹 `sqlite3`를 그대로 써도 이벤트 루프를
막지 않는다. 외부 HTTP도 `httpx.Client`(동기)를 쓴다.

| 축 | 동기 (선택) | 비동기 (대안) |
|----|------------|--------------|
| SQLite | `sqlite3` 표준 라이브러리 그대로 | `aiosqlite` 의존성 추가 |
| 외부 HTTP | `httpx.Client` | `httpx.AsyncClient` |
| 테스트 | `pytest`만 | `pytest-asyncio` + 이벤트 루프 픽스처 |
| 대가 | 요청당 스레드풀 슬롯 1개 소비 (동행 2~5명 규모, A6에서 문제 없음) | 의존성 2개·테스트 복잡도 증가 |

### 3.3 ORM을 도입하지 않는다

| 선택지 | 이득 | 대가 |
|--------|------|------|
| **표준 `sqlite3` + 수기 SQL (선택)** | 런타임 의존성 0 추가. `contracts`에 넣을 DDL이 곧 진실. WAL·`busy_timeout` 같은 PRAGMA를 직접 통제. 재정렬의 2단계 UPDATE(§6.10)를 그대로 표현 | 테이블 8개 분량의 CRUD SQL을 손으로 쓴다 |

## 5. 데이터 모델

### 5.1 엔티티 개요

| 엔티티 | 역할 | 키 |
|--------|------|-----|
| `trip` | 여행 1건. 초대코드와 **동기화 리비전**을 보유 | `id` (uuid4 hex) |
| `participant` | 무계정 참가자. 토큰은 **해시만** 저장(A10) | `id` |
| `day` | 여행의 하루(1~4). 날짜·색·기본 시작시각 | `id`, `UNIQUE(trip_id, day_index)` |
| `spot` | 방문 지점. 순서·좌표·영업시간 원문·체류시간·**낙관적 잠금 version** | `id`, `UNIQUE(day_id, position)` |
| `visit` | 완료 체크 1건(스팟당 최대 1) | `spot_id` (PK) |
| `expense` | 지출 1건. 금액은 **정수 minor unit** | `id`, `version` |
| `expense_share` | 지출의 분담액. **기록 시점에 확정 저장** | `(expense_id, participant_id)` |
| `external_cache` | 날씨·환율의 마지막 성공 응답 | `key` |
| `join_attempt` | 참여 시도 로그(IP 레이트 리밋) | `(ip, attempted_at)` 인덱스 |

**저장 규약 (NFR-013 · NFR-014)**

- 시각 컬럼 중 `*_at`은 **UTC ISO-8601** 문자열(`2026-10-05T01:23:45Z`). 표시·계산만 HKT.
- `date`는 HKT 기준 달력일 `YYYY-MM-DD`. `start_local`·`fixed_start_local`은 HKT `HH:MM`.
- 금액은 전부 `*_minor INTEGER` (HKD cent). **부동소수 금액 컬럼은 없다.**
- 좌표만 `REAL`이다(거리 계산 입력이며 금액이 아니다).

### 5.2 DDL (`src/harbor_lantern/storage/schema.sql`) — 그대로 구현

```sql
-- 연결마다 실행 (db.py). WAL 은 DB 파일 속성이라 1회면 남지만 멱등하게 매번 건다.
PRAGMA journal_mode = WAL;      -- O7: 다중 리더 + 단일 라이터
PRAGMA synchronous  = NORMAL;   -- WAL 에서 안전·성능 균형
PRAGMA foreign_keys = ON;       -- SQLite 는 기본이 OFF 다 (연결마다 켜야 한다)
PRAGMA busy_timeout = 5000;     -- 라이터 경합 시 즉시 SQLITE_BUSY 로 죽지 않게

CREATE TABLE IF NOT EXISTS trip (
  id            TEXT PRIMARY KEY,
  name          TEXT NOT NULL,
  start_date    TEXT NOT NULL,                       -- 'YYYY-MM-DD' (HKT)
  base_currency TEXT NOT NULL DEFAULT 'HKD',
  invite_code   TEXT NOT NULL UNIQUE,                -- 정규형 12자
  revision      INTEGER NOT NULL DEFAULT 1,          -- 동기화용 단조 증가 (DSN-21)
  created_at    TEXT NOT NULL                        -- UTC
);

CREATE TABLE IF NOT EXISTS participant (
  id           TEXT PRIMARY KEY,
  trip_id      TEXT NOT NULL REFERENCES trip(id) ON DELETE CASCADE,
  display_name TEXT NOT NULL,
  token_hash   TEXT NOT NULL UNIQUE,                 -- sha256(원문). 원문은 저장하지 않는다
  is_organizer INTEGER NOT NULL DEFAULT 0,
  joined_at    TEXT NOT NULL,
  UNIQUE (trip_id, display_name)
);
CREATE INDEX IF NOT EXISTS ix_participant_trip ON participant(trip_id);

CREATE TABLE IF NOT EXISTS day (
  id          TEXT PRIMARY KEY,
  trip_id     TEXT NOT NULL REFERENCES trip(id) ON DELETE CASCADE,
  day_index   INTEGER NOT NULL,                      -- 1..4
  date        TEXT NOT NULL,                         -- 'YYYY-MM-DD'
  title       TEXT NOT NULL,
  area        TEXT NOT NULL,
  color       TEXT NOT NULL,                         -- '#22d3ee'
  start_local TEXT NOT NULL,                         -- 'HH:MM' (HKT)
  UNIQUE (trip_id, day_index)
);

CREATE TABLE IF NOT EXISTS spot (
  id                TEXT PRIMARY KEY,
  trip_id           TEXT NOT NULL REFERENCES trip(id) ON DELETE CASCADE,
  day_id            TEXT NOT NULL REFERENCES day(id) ON DELETE CASCADE,
  position          INTEGER NOT NULL,                -- 0-based, 일자 내 연속
  time_label        TEXT NOT NULL,                   -- '오전' | '20:00' ...
  fixed_start_local TEXT,                            -- 'HH:MM' | NULL (고정시각 일정)
  name              TEXT NOT NULL,
  name_original     TEXT NOT NULL DEFAULT '',
  tip               TEXT NOT NULL DEFAULT '',
  hours_text        TEXT NOT NULL DEFAULT '',        -- 자유 문자열 원문 (파서 입력)
  closed_text       TEXT NOT NULL DEFAULT '',
  description       TEXT NOT NULL DEFAULT '',
  recommendation    TEXT NOT NULL DEFAULT '',
  lat               REAL NOT NULL,
  lng               REAL NOT NULL,
  dwell_minutes     INTEGER,                         -- NULL → 시간대 기본값 (O6)
  version           INTEGER NOT NULL DEFAULT 1,      -- 낙관적 잠금 (O7)
  created_at        TEXT NOT NULL,
  updated_at        TEXT NOT NULL,
  UNIQUE (day_id, position),
  CHECK (lat >= -90.0  AND lat <= 90.0),
  CHECK (lng >= -180.0 AND lng <= 180.0),
  CHECK (dwell_minutes IS NULL OR dwell_minutes >= 0)
);
CREATE INDEX IF NOT EXISTS ix_spot_trip ON spot(trip_id);
CREATE INDEX IF NOT EXISTS ix_spot_day  ON spot(day_id, position);

CREATE TABLE IF NOT EXISTS visit (
  spot_id TEXT PRIMARY KEY REFERENCES spot(id) ON DELETE CASCADE,
  trip_id TEXT NOT NULL REFERENCES trip(id) ON DELETE CASCADE,
  done_by TEXT NOT NULL REFERENCES participant(id) ON DELETE CASCADE,
  done_at TEXT NOT NULL                              -- UTC
);
CREATE INDEX IF NOT EXISTS ix_visit_trip ON visit(trip_id);

CREATE TABLE IF NOT EXISTS expense (
  id           TEXT PRIMARY KEY,
  trip_id      TEXT NOT NULL REFERENCES trip(id) ON DELETE CASCADE,
  payer_id     TEXT NOT NULL REFERENCES participant(id),
  amount_minor INTEGER NOT NULL CHECK (amount_minor > 0),
  currency     TEXT NOT NULL DEFAULT 'HKD' CHECK (currency = 'HKD'),
  note         TEXT NOT NULL DEFAULT '',
  spot_id      TEXT REFERENCES spot(id) ON DELETE SET NULL,
  spent_at     TEXT NOT NULL,                        -- UTC
  version      INTEGER NOT NULL DEFAULT 1,
  created_at   TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS ix_expense_trip ON expense(trip_id);

CREATE TABLE IF NOT EXISTS expense_share (
  expense_id     TEXT NOT NULL REFERENCES expense(id) ON DELETE CASCADE,
  participant_id TEXT NOT NULL REFERENCES participant(id) ON DELETE CASCADE,
  share_minor    INTEGER NOT NULL CHECK (share_minor >= 0),
  PRIMARY KEY (expense_id, participant_id)
);

CREATE TABLE IF NOT EXISTS external_cache (
  key        TEXT PRIMARY KEY,                       -- 'weather:hk' | 'fx:HKD-KRW'
  payload    TEXT NOT NULL,                          -- 정규화된 JSON (공급자 원문 아님)
  fetched_at TEXT NOT NULL                           -- UTC — 마지막 '성공' 시각
);

CREATE TABLE IF NOT EXISTS join_attempt (
  ip           TEXT NOT NULL,
  attempted_at TEXT NOT NULL                         -- UTC
);
CREATE INDEX IF NOT EXISTS ix_join_attempt ON join_attempt(ip, attempted_at);
```

**`currency`에 `CHECK (currency = 'HKD')`를 건 이유.** REQ-007이 통화 필드를 요구하고 A3이 기본
통화를 HKD로 못박았다. 이번 릴리스에서 다른 통화 입력을 받으면 정산(REQ-008)이 환율 가용성에
의존하게 되는데, 그 순간 NFR-004(환율은 실패할 수 있고 폴백한다)와 정면으로 충돌한다.
**환율이 없다고 정산이 멈추면 안 된다.** 그래서 필드는 남기되 값은 HKD로 잠근다.

**두 개의 "버전"을 혼동하지 말 것 (O7).**

| 이름 | 위치 | 용도 | 클라이언트 사용 |
|------|------|------|----------------|
| `spot.version` · `expense.version` | 리소스 행 | **낙관적 잠금**. 불일치 시 409 + 최신 리소스 | `PATCH` 요청 본문의 `version` |
| `trip.revision` | 여행 행 | **동기화**. 모든 변경 트랜잭션에서 +1 | `GET /state`의 `ETag` / `If-None-Match` |

`day`에는 `version`을 두지 않는다. 재정렬은 여러 행을 한꺼번에 바꾸므로 행 단위 잠금이 의미가 없고,
`expected_revision`(여행 단위)으로 막는 것이 정확하다(§6.10).

| `spot.closed` | `closed_text` | 원문 그대로 |

### 6.5 금액 (`domain/money.py`) — DSN-12 일부 (NFR-014 · AC-013 · AC-029)

```python
def split_even(amount_minor: int, participant_ids: Sequence[str]) -> dict[str, int]
def hkd_cent_to_krw(amount_minor: int, rate_micro: int) -> int
```

- `split_even`: `ids = sorted(participant_ids)`; `base, rem = divmod(amount_minor, len(ids))`;
  **앞에서 `rem`명에게 +1**. 합계는 항상 `amount_minor`와 정확히 일치한다(AC-013:
  `1000 ÷ 3 → 334, 333, 333`). 정렬 키가 참가자 ID이므로 입력 순서가 달라도 결과가 같다.
- `hkd_cent_to_krw`: 환율은 `rate_micro = round(rate * 1_000_000)` 정수로 들고 다닌다.
  `krw = (amount_minor * rate_micro + 50_000_000) // 100_000_000` — 정수 반올림(half-up).
  검산: 10000 cent × 171.23 → `(10000*171_230_000 + 5e7)//1e8 = 17123`원. **float 없음**(AC-029).
- KRW는 보조 단위가 없으므로 반환은 **원 단위 정수**다.

### 6.6 정산 (`domain/settle.py`) — DSN-13 (REQ-008 · AC-014~AC-016)

```python
def balances(paid: Mapping[str, int], owed: Mapping[str, int]) -> dict[str, int]
def settle(balances: Mapping[str, int]) -> list[Transfer]
```

`settle`은 최소 현금흐름 그리디다.

1. `creditors` = 잔액 > 0, `debtors` = 잔액 < 0.
2. creditors는 `(-amount, participant_id)`, debtors는 `(-abs(amount), participant_id)`로 정렬
   — 금액 내림차순, 동액이면 ID 오름차순. **정렬 규칙이 곧 결정론의 근거다**(AC-016).
3. 가장 큰 채권자와 가장 큰 채무자를 `min(a, b)`만큼 상계하고, 0이 된 쪽을 제거. 반복.
4. 결과를 `(from_participant_id, to_participant_id)` 오름차순으로 정렬해 반환.

매 단계에서 최소 한 명이 0이 되므로 송금 건수는 **n-1 이하**다(AC-015). 잔액이 전부 0이면 빈 목록.

AC-014 검산: A `+2000`, B `-700`, C `-1300` → C→A 1300, B→A 700 → 2건, 합 0 ✓.

### 6.7 이동시간 엔진 (`domain/travel.py`) — DSN-14 (REQ-010 · O2 · AC-020)

```python
def leg(a: LatLng, b: LatLng, cfg: TravelConfig) -> Leg
def day_totals(legs: Sequence[Leg]) -> tuple[float, int]   # (총 거리 m, 총 이동 분)
```

```
d      = haversine_m(a, b)

speed  = cfg.walk_speed_kmh       if walk else cfg.transit_speed_kmh     # km/h

                                        round_half_up((travel_seconds + overhead_seconds) / 60))
```

**계수는 전부 추정치다** — 실제 경로탐색이 아니다(A8 · Won't). 화면과 API 응답 모두
`estimated: true`를 달고 다닌다(AC-020).

| 계수 | 기본값 | 근거 (전부 추정) |
|------|--------|-----------------|
| 도보 우회계수 | 1.35 | 직선거리 → 가로망 실제 보행거리 보정 |
| 대중교통 우회계수 | 1.45 | 역 접근 + 노선 우회 |
| 모드 전환 임계 | 1200 m | 이 이하는 걷는 편이 빠르다는 판단 |
| 도보 평균속도 | 4.8 km/h | 성인 평균 보행 |
| 대중교통 실효속도 | 22.0 km/h | MTR·버스 혼합, 정차 포함 |
| 환승·대기 고정 여유 | 8 분 | 개찰·플랫폼 대기·환승 |
| 최소 구간 시간 | 1 분 | 거리 > 0인데 0분이 뜨는 것을 막는다 |

> **AC-020의 "비례" 함정.** 대중교통 모드에는 **덧셈 항**(환승 여유)이 있어서 우회계수를 2배로 해도
> `minutes`가 2배가 되지 않는다. 비례성은 **곱해지는 주행 성분**에 대해서만 성립하므로,
> ① 검증은 `travel_seconds`(환승 여유 제외)에 대해 하고 ② 테스트는 환승 여유가 0인 **도보 모드**를
> 쓴다. `Leg`가 `travel_seconds`와 `overhead_seconds`를 따로 노출하는 이유가 이것이다.

### 6.9 영업시간 파서 (`domain/hours.py`) — DSN-16 (REQ-012 · O4 · AC-022 · AC-024)

**대원칙 (R1 · AC-024): 못 읽으면 `unknown`이고, `unknown`은 경고를 만들지 않는다.**
거짓 경고 하나가 진짜 경고 전부를 무시하게 만든다. 파서는 **추측하지 않는다.**

전처리: NFKC 정규화 → `–`·`—`·`~`·`〜`를 `-`로 → 연속 공백 축약.

규칙을 **위에서부터 순서대로** 적용하고, 처음 맞는 것을 채택한다.

| # | 패턴 | 판정 | 시드 예시 |
|---|------|------|----------|
| P-01 | `평일 A-B / (주말·공휴일\|주말\|공휴일) C-D` | 요일별 개방(`weekday_open`: 월~금 A-B, 토·일 C-D) | `"평일 10:00–18:00 / 주말·공휴일 09:00–18:30"` |
| P-02 | 괄호 `(...)` 세그먼트 제거 후 재평가 | 보조 설명은 버린다 | `"매일 10:00–23:00 (갤러리 화~일 11:00–19:00)"` → `10:00-23:00` |
| P-03 | `/` 또는 `·`로 나눈 세그먼트 중 **시간 표현(범위 또는 `상시`)을 가진 것이 2개 이상** | `unknown` — 서로 다른 주체 | `"단지 상시 · 상점 대략 11:00–20:00"`, `"하행 06:00–10:00 / 상행 10:00–24:00"` |
| P-04 | 남은 텍스트에 `HH:MM-HH:MM` 범위가 **정확히 1개** | `open_range`. `close <= open`이면 `crosses_midnight` | `"매일 08:00–18:00 · 무료"`, `"AEL 대략 05:50–00:48"` |
| P-05 | 범위 0개 + `상시` 또는 `24h` | `open_24h` | `"야외 상시"`, `"야외 상시 (24h)"` |
| P-06 | `HH:MM`이 1개뿐이고 범위가 아님(`시작` 등) | `unknown` — 이벤트지 영업시간이 아니다 | `"매일 20:00 시작 · 약 10~13분"` |

- **`6~10분 간격`처럼 `HH:MM` 형태가 아닌 숫자 범위는 시간 범위로 읽지 않는다** — 정규식이
  `\d{1,2}:\d{2}`를 요구하기 때문. `"매일 06:30–23:30경 · 6~10분 간격"`은 P-04로 `06:30-23:30`,

### 6.11 재정렬·이동의 원자성 — DSN-10 (REQ-005 · NFR-012 · AC-008 · AC-009 · AC-047)

`UNIQUE(day_id, position)`이 걸려 있으므로 순서를 **한 번에 갈아끼우면 중간 상태에서 충돌**한다.
그래서 한 트랜잭션 안에서 2단계로 쓴다.

```sql
BEGIN IMMEDIATE;
  -- 1단계: 대상 일자의 position 을 음수 영역으로 대피 (UNIQUE 충돌 회피)
  UPDATE spot SET position = -(position + 1) WHERE day_id = ?;
  -- 2단계: 요청 순서대로 0..n-1 재부여
  UPDATE spot SET position = ?, updated_at = ? WHERE id = ? AND day_id = ?;
  -- 일자 간 이동이면 day_id 도 함께 바꾸고 양쪽 일자를 모두 2단계 처리
  UPDATE trip SET revision = revision + 1 WHERE id = ?;
COMMIT;
```

- `BEGIN IMMEDIATE`로 시작한다. SQLite의 기본 `DEFERRED`는 첫 쓰기에서야 라이터 락을 잡아
  읽고-쓰기 사이에 다른 라이터가 끼면 `SQLITE_BUSY`가 늦게 터진다.
- 요청 본문의 `spot_ids`가 그 일자의 스팟 집합과 **정확히 일치**하지 않으면 422로 거부하고
  **아무것도 쓰지 않는다**(AC-047 롤백).
- 일자 간 이동(AC-009)은 **원본·대상 두 일자를 같은 트랜잭션에서** 재부여한다. 결과적으로 양쪽 모두
  0부터 연속이다.
- 동시 편집 방어는 본문의 `expected_revision`이 맡는다. 불일치면 409 + 최신 상태.

### 6.12 고정시각 충돌 (`domain/conflict.py`) — DSN-18 (REQ-013 · AC-025)

```python
def find_conflicts(scheduled: Sequence[ScheduledSpot],
                   fixed: Mapping[str, int]) -> list[Conflict]   # fixed: spot_id -> 분
```

`fixed_start_local`이 있는 스팟 F에 대해, **일자 내에서 F보다 앞 순서인 마지막 스팟 P**의
`depart_min`이 `fixed[F]`를 **초과하면**(`>`) 충돌 1건.

```
overlap_start = fixed[F]
overlap_end   = depart_min(P)
overlap_minutes = overlap_end - overlap_start
```

AC-025 검산: P가 19:50(1190분) 도착 + 40분 체류 → depart 20:30(1230분). F = 20:00(1200분).
`1230 > 1200` → 충돌 1건, 구간 `20:00~20:30`, 30분, 두 스팟 ID 포함 ✓.
체류를 10분으로 줄이면 depart = 1200, `1200 > 1200`이 거짓 → 0건 ✓ (**비교는 반드시 `>`,
`>=`면 딱 맞는 일정이 충돌로 잡힌다**).

### 6.13 외부 공급자 — DSN-20 (REQ-014 · REQ-015 · O1 · NFR-003 · NFR-004)

**두 공급자 모두 API 키가 없다.** 아래 응답은 2026-09-13에 실제로 호출해 받은 것이다.

| | 날씨 | 환율 |
|---|------|------|
| 공급자 | Open-Meteo | Frankfurter |
| 엔드포인트 | `GET https://api.open-meteo.com/v1/forecast` | `GET https://api.frankfurter.dev/v1/latest` |
| 파라미터 | `latitude=22.3193&longitude=114.1694&current=temperature_2m,relative_humidity_2m,precipitation,weather_code&daily=temperature_2m_max,temperature_2m_min,precipitation_probability_max,weather_code&timezone=Asia%2FHong_Kong&forecast_days=1` | `base=HKD&symbols=KRW` |
| 키 | 불필요 | 불필요 |
| 실측 응답(요약) | `{"current":{"time":"2026-09-13T15:00","interval":900,"temperature_2m":28.0,"relative_humidity_2m":79,"precipitation":0.0,"weather_code":3},"daily":{"time":["2026-09-13"],"temperature_2m_max":[28.2],"temperature_2m_min":[24.4],"precipitation_probability_max":[100],"weather_code":[96]}}` | `{"amount":1.0,"base":"HKD","date":"2026-09-11","rates":{"KRW":171.23}}` |
| **TTL** | **900초** | **21600초 (6시간)** |
| TTL 근거 | 응답 자신이 `current.interval: 900`을 준다 — 15분보다 자주 물어도 새 값이 없다 | ECB는 영업일 16:00 CET에 1회 갱신. **실측이 이를 확인해 준다**: 2026-09-13(토) 조회에 `date: 2026-09-11`(금)이 돌아왔다 |
| 조회일 | 2026-09-13 | 2026-09-13 |

**Frankfurter의 `date`는 조회일이 아니다.** 주말·공휴일에는 직전 영업일 값이 온다. 이것은 고장이
아니므로 `stale`로 표시하지 않고 **별도 필드 `rate_date`**로 그대로 노출한다. `stale`은 오직
"우리 캐시가 만료됐는데 갱신에 실패했다"를 뜻한다. 둘을 섞으면 사용자가 매 주말 고장 신고를 한다.

```python
class WeatherPort(Protocol):
    def fetch(self) -> WeatherSnapshot: ...        # 실패 시 ExternalUnavailable 를 던진다
class FxPort(Protocol):
    def fetch(self) -> FxSnapshot: ...

class CachedProvider:                              # services/external/cache.py
    def __init__(self, port, key: str, ttl_s: int, db, clock, lock: threading.Lock): ...
    def get(self) -> CachedResult: ...
```

`CachedProvider.get()` 흐름:

1. `external_cache`에서 `key` 조회.
2. 있고 `now - fetched_at < ttl` → **어댑터 호출 없이** 반환 (`stale=False`). AC-026의 "호출 횟수 0".
3. 만료 또는 없음 → **키별 `threading.Lock`을 잡고** 다시 확인(더블 체크) 후 `port.fetch()` 1회.
   락이 없으면 동시 요청 n건이 각각 외부를 때린다 — AC-026의 "1회 호출"이 깨진다.
4. 성공 → 정규화 JSON을 캐시에 upsert, `stale=False` 반환.
5. 실패(타임아웃 · 5xx · JSON 파싱 실패 · 필드 누락) → **예외를 밖으로 내지 않는다.**
   캐시가 있으면 `stale=True` + `fetched_at`으로 200 반환(AC-027 · AC-038),
   캐시가 없으면 `available=false`로 200 반환. **어떤 경우에도 5xx를 만들지 않는다.**

어댑터는 공급자 원문을 **정규화된 우리 형태**로 바꿔서 캐시에 넣는다. 공급자가 필드를 바꿔도
캐시에 남은 과거 데이터가 계속 읽히게 하려면 이 경계가 필요하다.

```
WeatherSnapshot: temp_c, humidity_pct, precipitation_mm, weather_code,
                 today_max_c, today_min_c, precip_prob_pct, observed_local
FxSnapshot:      base='HKD', quote='KRW', rate_micro:int, rate_date:'YYYY-MM-DD'
```

`rate_micro = round(rates["KRW"] * 1_000_000)` — 환율도 **정수로 굳혀서** 저장한다(NFR-014).

**테스트(NFR-003 · AC-037)**: `tests/conftest.py`가 `socket.socket.connect`·`socket.create_connection`을
가로채 루프백이 아닌 목적지에 대해 즉시 예외를 던진다. FastAPI `TestClient`는 ASGI 인프로세스
전송이라 소켓을 열지 않고, `sqlite3`도 열지 않으므로 이 차단은 **오직 실수로 남은 아웃바운드
호출만** 잡는다.

### 6.14 동기화 — DSN-21 (REQ-016 · O3 · AC-035 · AC-036)

**리비전 ETag를 고른다.** 변경분(delta) 페이로드는 "무엇이 바뀌었나"를 서버가 추적해야 하고
(변경 로그 테이블 + 가비지 수집), 잘못 계산하면 **조용히 화면이 어긋난다** — 27스팟 전체 상태가
수십 KB에 불과한데 치를 값이 아니다.

- 모든 변경 트랜잭션이 `trip.revision`을 +1 (AC-035).
- `GET /api/trips/{trip_id}/state` → 헤더 `ETag: "<revision>"`, 본문에 `revision`.
- 클라이언트는 `If-None-Match: "<revision>"`을 보낸다. 같으면 **304 · 본문 없음**,
  다르면 200 + 전체 상태(AC-036).
- 폴링 주기 10초. `document.visibilityState === 'hidden'`이면 **정지**, 복귀 시 즉시 1회.
  연속 실패 시 10 → 20 → 40초(상한 60초) 백오프.

> **함정 — `/state`에 "지금"을 넣지 마라.** ETag가 리비전만으로 만들어지므로, 응답 본문이
> 서버의 현재 시각에 따라 달라지면 **304가 거짓말을 한다**(내용이 바뀌었는데 안 바뀌었다고 답한다).
> 그래서 `/state`의 모든 계산은 일자 `date`·`start_local`·스팟 데이터만 입력으로 쓴다. 현재 시각이
> 필요한 것(현지 시계, "지금 열려 있나")은 **클라이언트가** 계산한다. 날씨·환율은 `/state`가 아니라
> 별도 엔드포인트다.

### 6.16 동선 최적화 (`domain/route.py`) — DSN-19 (REQ-009 · AC-017 · AC-018)

```python

                 coords: Mapping[str, LatLng],

```

  자유 스팟만 남은 자리에 재배치한다. 이것으로 "시각 순서상의 자리 유지"(AC-018)가 구조적으로 보장된다.

  개선이 없을 때까지 최선-개선 방식으로 반복. 인덱스 쌍을 오름차순 고정 순회, 동률이면 먼저 나온 것).

  **현재 순서를 그대로** 돌려준다(`improved: false`). 부등식이 절대 깨지지 않는다.
- 동률 시 타이브레이크는 스팟 ID 시퀀스의 사전순 최소 — 같은 입력에 같은 출력(AC-018).

  `PUT /days/{n}/order`가 한다(REQ-009의 "적용 여부를 고르고 싶다"). 쓰기 경로를 늘리지 않는 것이
  §6.11의 원자성 설계를 한 곳에 유지하는 방법이다.

```
RouteProposal: current_order[], proposed_order[], current_total_distance_m,
               proposed_total_distance_m, improved: bool,
               algorithm: "exact" | "two_opt", anchored_spot_ids[]
```

### 6.17 참여와 레이트 리밋 — DSN-08 (REQ-003 · NFR-006 · AC-004 · AC-005 · AC-040)

`POST /api/join` 처리 순서 — **순서가 곧 보안 속성이다.**

1. `join_attempt`에서 `(ip, now - window)` 이후 시도 수를 센다. `>= 10`이면 **429 + `Retry-After`**
   (코드 유효성을 보기 전에 막는다).
2. 시도를 기록한다(성공·실패 무관).
3. `display_name` 검증 — 공백 제거 후 길이 1~24가 아니면 **422**. 이것만이 422다.
4. `normalize_code(invite_code)`. `None`이거나 매칭 여행이 없으면 **404** — 두 경우가
   **완전히 같은 본문**(`{"error":"invite_not_found","message":"초대코드를 찾을 수 없습니다."}`)이다.
5. 같은 여행에 같은 표시명이 있으면 409(`UNIQUE(trip_id, display_name)`).
6. 토큰 발급: `secrets.token_urlsafe(32)`. **DB에는 `sha256(token)`만** 저장한다(A10).
   원문은 이 응답에서 한 번만 나가고 다시는 조회할 수 없다.

레이트 리밋 카운터는 DB 테이블이다(인메모리가 아니다). 이유: 시계를 주입하면 그대로 결정론
테스트가 되고(AC-040), 프로세스 재시작으로 카운터가 리셋되지 않는다. `attempted_at < now - window`
행은 같은 트랜잭션에서 삭제한다.

인증: 모든 여행 스코프 엔드포인트는 `X-Participant-Token` 헤더를 요구한다.
`sha256`으로 조회 → 참가자 → 그 참가자의 `trip_id`가 경로의 `trip_id`와 다르면 **404**(403이 아니다 —
존재 여부를 알려 주지 않는다).

### 6.18 스팟 CRUD와 낙관적 잠금 — DSN-09 (REQ-004 · NFR-012 · AC-006 · AC-007 · AC-047)

| 동작 | 엔드포인트 | 규칙 |
|------|-----------|------|
| 생성 | `POST /trips/{id}/days/{n}/spots` | 201 + 리소스. `position = max+1`(목록 끝). 위도 `[-90,90]`·경도 `[-180,180]` 벗어나면 422 (Pydantic `ge`/`le` + DDL `CHECK` 이중) |
| 수정 | `PATCH /trips/{id}/spots/{sid}` | 본문에 `version` 필수. `UPDATE ... WHERE id=? AND version=?`의 `rowcount == 0`이면 **409 + 최신 리소스**. 성공 시 `version + 1`, `updated_at` 갱신 |
| 삭제 | `DELETE /trips/{id}/spots/{sid}` | 204. 같은 트랜잭션에서 남은 스팟의 `position`을 0..n-1로 재부여(§6.11의 2단계 방식) — 빈 자리를 남기지 않는다(AC-008) |

`version` 비교는 **SQL의 `WHERE` 절에서** 한다. 파이썬에서 읽고 비교한 뒤 쓰면 그 사이가 경합
창이다. `rowcount`가 유일하게 믿을 수 있는 신호다.

삭제 시 진행률 분모가 1 줄어드는 것(AC-007)은 `visit`의 `ON DELETE CASCADE`와 분모를
`COUNT(spot)`로 계산하는 것으로 자동 충족된다.

### 6.19 완료 체크와 진행률 — DSN-11 (REQ-006 · AC-010 · AC-011 · AC-030)

`PUT /trips/{id}/spots/{sid}/done` 본문 `{"done": true|false}` — 멱등이다.
`true`면 `INSERT OR REPLACE INTO visit(spot_id, trip_id, done_by, done_at)`, `false`면 `DELETE`.
`done_by`는 요청 토큰의 참가자, `done_at`은 주입된 시계의 UTC.

응답과 `/state`의 스팟마다:
`done: {is_done, by_participant_id, by_display_name, at}` (미완료면 `is_done:false`, 나머지 null).
저장이 서버에 있으므로 참가자 B의 조회에도 그대로 보인다(AC-011).

진행률: `percent = round(done / total * 100)`, `total == 0`이면 **0** (0으로 나누지 않는다 — AC-030).
파이썬 `round()`는 은행가 반올림이라 `.5`에서 참조 HTML의 JS `Math.round`와 갈린다.
`percent`는 `domain`의 `round_half_up` 헬퍼를 쓴다(프론트의 진행률 링은 서버 값을 그대로 그린다).

### 6.20 경비 API — DSN-12 (REQ-007 · AC-012 · AC-013)

`POST /trips/{id}/expenses` 본문:
`{payer_id, amount_minor, currency:"HKD", note, spot_id?, spent_at?, share_participant_ids[]}`

- `amount_minor <= 0` → 422. `share_participant_ids`가 비었으면 → 422 (AC-012).
- 지정된 참가자가 그 여행 소속이 아니면 422.
- 한 트랜잭션에서 `expense` 1행 + `expense_share` n행(`split_even` 결과) + `trip.revision + 1`.
- **분담액은 기록 시점에 확정해 저장한다.** 나중에 참가자가 추가돼도 과거 지출의 분담이 흔들리지
  않는다. 정산은 저장된 `share_minor`를 그대로 더한다 — 재계산 드리프트가 원천적으로 없다.

`GET /trips/{id}/expenses`는 각 항목에 `amount_krw`를 붙인다. 환율이 `available:false`면
`amount_krw: null`이고 `amount_minor`는 정상 반환된다(AC-029).

`GET /trips/{id}/settlement` → `{balances: [{participant_id, display_name, balance_minor}],
transfers: [{from_participant_id, to_participant_id, amount_minor}], currency: "HKD"}`.
`sum(balance_minor) == 0`을 서버가 assert 한다(NFR-014).

### 6.21 근처 장소 어댑터와 위치 키 캐시 — DSN-26 (REQ-017 · AC-050~AC-056)

**공급자**: OpenStreetMap Overpass `POST https://overpass-api.de/api/interpreter`
(API 키 불필요 · 조회일 2026-09-14 · 출처 `https://wiki.openstreetmap.org/wiki/Overpass_API`).
`nwr`로 노드·웨이·릴레이션을 한 번에 묻고 `out center`로 웨이·릴레이션의 중심 좌표를 받는다.

**왜 기존 `CachedProvider`를 쓰지 않는가.** 그것은 **키 하나짜리 싱글턴**이다(날씨·환율은
인자가 없다). 근처 조회는 질의마다 키가 달라지므로 그 안에 욱여넣으면 날씨·환율 경로에
회귀 위험이 생긴다. `services/external/nearby.py`에 **위치 키 캐시**를 따로 둔다.

| 결정 | 값 | 근거 |
|------|-----|------|
| 캐시 키 | `nearby:{카테고리}:{lat_q}:{lng_q}:{반경}` | 좌표를 소수 3자리(≈110m)로 **양자화** — 걸어 다니며 몇십 미터 움직여도 같은 항목을 맞힌다(AC-054) |
| TTL | 1800초 | 식당·카페는 분 단위로 바뀌지 않는다. 공용 무료 서비스에 매 요청 질의를 보내면 429를 받는다 |
| 락 | **키별 락** (dict + dict 보호 락) | 만료 순간 동시 요청이 전부 외부로 나가는 것을 막는다(§12 F6) |
| 결과 상한 | 50건 | 남의 서버에 과한 질의를 보내지 않는다 |
| 반경 | 기본 800m · 100~3000m | 계약(`/api/nearby`)과 `config` 상수가 **같은 자리**를 쓴다 |

**거리와 길찾기 URL은 캐시에 넣지 않는다.** 캐시 키가 양자화돼 있으므로 거리를 함께
저장하면 최대 110m 어긋난 값이 굳는다. 둘 다 요청이 **실제로 보낸 좌표**로 응답 조립
시점에 계산한다(`PlaceSnapshot`이 그 필드를 갖지 않는 것이 이 결정의 강제 수단이다).

**카테고리의 SSoT는 `config.NEARBY_CATEGORIES` 표 하나다.** 어댑터의 질의도, API가 받는
값도, 화면의 라벨도 전부 여기서 나온다. 늘리려면 한 줄을 더하고 `enabled=True`로 두면
된다. 지금 켜진 것은 `restaurant`·`cafe`·`fast_food`이고, `attraction`은 확장 지점이
실제로 동작함을 보이는 자리로 `enabled=False`다 — **꺼진 카테고리 요청은 422**다(조용히
무시하면 "결과 없음"과 구분되지 않는다).

**토큰을 요구하지 않는다.** 여행에 속한 데이터가 아니라 공개 지리 정보이며 weather/fx와
같은 성격이다. 토큰을 요구하면 "가입 전에 근처를 둘러본다"가 막힌다.

### 6.22 근처 장소 화면 — DSN-27 (REQ-017 · REQ-018 · AC-057)

- `mapbar`에 **"근처 맛집"** 토글. 위치가 꺼져 있으면 **조회하지 않고 안내**한다 —
  좌표 없이 부르면 서버가 422로 거절하는데, 그 422를 사용자에게 그대로 보여 줄 이유가 없다.
- 지도에 **별도 레이어**(`nearbyMarkers`). 일정 스팟은 번호가 박힌 물방울, 근처 장소는
  점이다 — **같은 모양이면 "내 일정"과 "그냥 근처 가게"가 지도에서 구분되지 않는다.**
- `stale: true`면 **마지막 조회 시각을 함께 표시**한다(NFR-004의 화면 쪽 귀결).
- **"일정에" 버튼**은 기존 스팟 생성 API를 그대로 탄다(REQ-018). 별도 경로를 만들지
  않으므로 타임라인·이동시간·경고·진행률이 자동으로 반영된다(AC-057).
- 근처 목록은 `store.nearby`에 두고 **여행 상태와 섞지 않는다.** 서버가 준 여행 데이터가
  아니라 휘발성 조회 결과이고, 폴링 동기화 대상도 아니다.
- 브라우저는 Overpass를 **직접 부르지 않는다.** 서버가 부른다 — 외부 도메인 참조를 늘리면
  `tests/static/test_frontend_assets.py`가 잡는다(AC-042).

### 6.23 무료 리뷰 API 조사 결과 — 왜 큐레이션인가 (REQ-019 · DSN-28)

근처 검색(REQ-017)은 OpenStreetMap 데이터라 **평점·후기가 없다**(실측: 침사추이 60곳의
태그 중 평점 계열 0건). "무료로 리뷰를 붙일 수 있나"를 조사한 결과가 아래다 —
**쓸 수 있는 것이 없었다**(조회일 2026-09-15).

| 후보 | 리뷰 | 왜 못 쓰는가 |
|------|------|-------------|
| Google Places (New) | 있음 | `reviews` 필드가 **Enterprise + Atmosphere SKU**($40/1,000콜)이고 프로젝트에 **결제 활성화 필수** |
| Foursquare | 유료만 | 무료 공개 데이터(FSQ OS Places, Apache 2.0)는 **POI 기본 22속성뿐 — 평점·팁 없음** |
| TripAdvisor Content API | 있음 | **폐지**(Terra 이관). Terra 는 등급제이며 무료 한도를 공개하지 않는다 |
| OpenRice (홍콩 1위) | 있음 | **공개 API 없음.** 스크래퍼·리셀러만 존재 — 공개 저장소에 넣을 것이 아니다 |
| OpenStreetMap | 없음 | 지도이지 리뷰 사이트가 아니다 |

**그래서 방향을 바꿨다.** 크라우드 평점을 가져오는 대신 **미쉐린 등급이라는 공개된 사실**을
미리 조사해 저장소에 넣는다. 리뷰 본문은 **링크로 넘긴다**(구글맵·OpenRice 검색) — 우리가
퍼오지 않으므로 비용도 약관 위험도 없다.

**좌표를 붙이려다 배운 것.** OSM 이름 일치로 85%를 얻었다고 생각했으나 가짜였다:

| 시도 | 결과 |
|------|------|
| Nominatim 상호명 검색 | 97건 **전부 빈 배열**(주소 검색기이지 POI 이름 검색기가 아니다) |
| Overpass 이름 일치 + 접두 폴백 | 85% — 그러나 **중복 검사에서 서로 다른 식당 여럿이 한 POI 로 묶인 것**이 드러났다(짧은 이름 POI 가 긴 이름을 삼켰다) |
| 폴백 제거 · 모호 항목 배제 | 11곳 — **역지오코딩 전수 대조에서 또 틀린 것**: `Duddell's`는 센트럴이 아니라 공항 지점, `Amber`는 타이항의 동명 가게 |
| Wikidata SPARQL | 0건 |

지점이 여럿이거나 동명 가게가 있으면 **이름만으로는 가를 수 없다.** 그래서 좌표는
"이름 → 주소(웹) → 주소 지오코딩" 2단계로 확인한 것만 넣고, **확인 못 한 곳은 비운다.**

**설계 규칙 셋.**

1. **좌표 없는 항목을 목록에서 빼지 않는다.** 빼면 사용자는 "홍콩에 미쉐린이 몇 곳뿐"이라고
   읽는다. 거리 정렬에서 뒤로 밀되 남긴다(정렬 키를 둘로 나눈다 — `None`과 float 을 한
   키에 섞으면 `TypeError` 로 터진다).
2. **출처와 한계를 응답에 항상 싣는다.** 출처 없는 추천 목록은 그냥 누군가의 취향이고,
   빕구르망 83곳이 빠졌다는 사실을 모르면 이 목록을 "홍콩 맛집 전부"로 읽는다.
3. **외부 호출도 캐시도 없다.** 저장소 안의 고정 파일이므로 `nearby` 의 TTL·stale·
   single-flight 기계가 필요 없다. 두 기능을 같은 틀에 넣으려 하지 않는다.

**에러 본문은 하나의 모양만 쓴다**: `{"error": "<코드>", "message": "<한국어 설명>", "detail": {...}?}`.
409에는 `detail.current`에 최신 리소스가, 429에는 `Retry-After` 헤더가 실린다.

날씨·환율이 **항상 200**인 것은 NFR-004 때문이다. 실패는 상태코드가 아니라 본문의
`available`·`stale`로 표현한다 — 위젯 하나가 죽어도 앱 전체가 죽지 않게 하려면 그래야 한다.

## 8. 성능 — DSN-23 (NFR-010 · O8 · AC-043)

**아래는 목표치이고 측정값이 아니다.** 절대치는 실행 환경에 의존한다(A6).

| 대상 | 지표 | 목표 |
|------|------|------|
| `GET /state` (27스팟, 타임라인·경고·충돌 전량 재계산) | p50 | ≤ 50 ms |
| 같음 | p95 | ≤ 120 ms |
| `POST /days/{n}/optimize` (자유 9스팟, 2-opt) | p95 | ≤ 150 ms |
| 위 전부 | **파탄 상한** | p95 > 1000 ms이면 CI 실패 |

- 측정 대상은 **서버 핸들러 내부 처리시간**이다(네트워크·브라우저 제외). 미들웨어가
  `X-Process-Time` 헤더로 노출하고 하네스가 이를 수집한다.
- `tools/perf_report.py` — 27스팟 시드 여행을 임시 DB에 만들고 워밍업 20회 후 200회 측정,
  `reports/perf.json`(기계용) + `reports/perf.md`(사람용)에 p50/p95/p99·표본수·파이썬 버전·플랫폼을
  남긴다(AC-043).
- **CI는 목표치로 실패하지 않는다.** 러너 성능이 흔들리면 게이트가 간헐적으로 빨개지고,
  간헐적 실패는 아무도 안 보게 된다. 실패는 파탄 상한(1000 ms)에서만 — 그건 성능 문제가 아니라
  알고리즘이 잘못된 신호다.

## 12. 설계 리스크와 구현 시 함정

01의 R1~R5에 더해, **설계 과정에서 새로 드러난 함정**을 남긴다. 전부 "조용히 틀리는" 종류라
테스트가 없으면 릴리스까지 살아남는다.

| # | 함정 | 왜 조용한가 | 방어 |
|---|------|------------|------|
| F1 | `/state` 응답에 서버 현재 시각을 넣으면 **ETag가 거짓말을 한다** | 304를 받은 클라이언트는 화면을 갱신하지 않는다. 로그에도 에러가 없다 | `/state` 계산 입력에서 `now` 제거(§6.14). `FixedClock`을 두 번 다르게 놓고 같은 본문이 나오는지 assert |
| F2 | 재정렬을 한 번에 UPDATE 하면 `UNIQUE(day_id, position)`가 중간 상태에서 터진다 | 스팟이 2개일 때는 우연히 통과하고 3개 이상 · 특정 순열에서만 실패한다 | 2단계(음수 대피 → 재부여) UPDATE(§6.11) + 27스팟 전 순열 일부에 대한 테스트 |
| F3 | `version`(리소스 잠금)과 `revision`(여행 동기화)을 혼동 | 둘 다 정수 카운터라 타입 검사가 안 잡는다. 잘못 쓰면 409가 안 나거나 남발된다 | 이름·위치를 §5.2 표로 고정. `PATCH`는 `version`, 재정렬은 `expected_revision`만 받는다 |
| F4 | 파이썬 `round()`는 은행가 반올림 — 진행률 `round(0.5)`가 0이 된다 | JS `Math.round`와 갈리는데 27개 중 특정 개수에서만 다르다 | `domain/util.round_half_up` 하나만 쓴다(§6.19). `round()` 직접 호출을 ruff 규칙/테스트로 금지 |
| F5 | `PRAGMA foreign_keys`는 **연결마다** 켜야 한다(기본 OFF) | 켜지 않아도 모든 테스트가 통과한다 — 다만 CASCADE가 안 돌아 고아 행이 쌓인다 | `db.py`가 연결 생성 직후 무조건 실행(§5.2). 삭제 후 고아 행 0을 assert |
| F6 | 캐시 만료 시 동시 요청이 각각 외부를 호출 | 단일 요청 테스트로는 절대 안 잡힌다. AC-026의 "1회 호출"이 부하에서만 깨진다 | 키별 `threading.Lock` + 더블 체크(§6.13). 스레드 2개로 동시 호출해 카운터 1 assert |
| F7 | 잘못된 형식의 초대코드에 422를 주면 열거 신호가 된다 | 기능은 멀쩡히 동작한다. 보안 속성만 조용히 사라진다 | 형식 오류도 **존재하지 않는 코드와 동일한 404 본문**(§6.4 · AC-040) |
| F8 | AC-020의 비례성을 대중교통 모드로 검증하면 실패한다 | 환승 여유가 덧셈 항이라 2배가 안 된다 | `travel_seconds`/`overhead_seconds` 분리 노출 + 도보 모드로 검증(§6.7) |
| F9 | 영업시간 파서가 "잘 읽으려고" 애쓰면 거짓 경고가 생긴다 | 경고가 하나 더 뜰 뿐 아무것도 안 터진다. 그러다 진짜 경고를 아무도 안 본다 | 규칙 7개 밖은 전부 `unknown`, `unknown`은 경고 0(§6.9 · R1 · AC-024) |
| F10 | `zoneinfo.ZoneInfo("Asia/Hong_Kong")`이 Windows에서 `tzdata` 없이 실패 | CI(리눅스)에서는 통과하고 개발자 PC에서만 터진다 | HKT는 UTC+8 고정 상수(§2.3). `zoneinfo` import를 정적 검사로 금지 |
| F11 | Leaflet 벤더 파일을 빠뜨린 채 `index.html`만 고치면 지도가 통째로 죽는다 | 로컬에 CDN 캐시가 남아 있으면 개발자 브라우저에서는 잘 보인다 | `tools/vendor_check.py` + `MANIFEST.sha256` 검증을 게이트에 포함(AC-042) |
| F12 | 터치 타깃 44px가 `padding`만으로 "대략 맞는" 상태 | 폰트·브라우저에 따라 43.5px가 된다. 화면상 차이가 안 보인다 | `min-width`·`min-height`를 **명시**하고 CSS 텍스트를 정적 검사(AC-044) |

## 16. 도시 가이드 확장 설계 (v1.5 · 2026-09-16 · DSN-31~DSN-50)

01 문서 §9 가 정의한 것은 "임의의 도시에서도 홍콩 가이드 수준의 일정을 받는다"이다.
이 장은 그것을 REQ-022~030 · NFR-017~020 단위로 전개한다.

**이 장의 모든 전제는 실측이다.** 수치는 `docs/_recon.md` 2026-09-15 정찰에서만 인용하고
(§16.21 출처표), 아직 재지 않은 것은 **재지 않았다고 쓴다.** 굽기 전에 알 수 없는 값을
설계서에 적어 두면 Phase 4 가 그것을 기준으로 삼는다 — 그건 측정이 아니라 자기확인이다.

### 16.1 이번 확장이 고쳐야 하는 것 (한 문단)

현재 자동 추천은 Overpass 결과를 후보로 쓴다. 그 후보 집합이 망가져 있다 —
파리 300건(상한) 중 138건이 상업 화랑, 오사카 300건 중 162건이 동네 놀이터였고
**에펠탑·루브르·오르세는 목록에 아예 없었다**(정찰 실측). 랭킹을 뒤에 붙여 고칠 수 있는
문제가 아니다. 가져오지도 못한 것은 정렬할 수 없다. 그래서 **후보를 뽑는 단계**를 바꾼다.

#### 16.1.1 품질 기대치 — 무엇이 되고 무엇이 안 되는지 (실측)

**"홍콩 가이드와 동급"이라고 쓰지 않는다.** 2026-09-15 측정에서 **기존 홍콩 가이드를 이 방식으로
재현해 봤다** — 상위 25건 중 한국어가 12건이고 **'주룽 모스크'가 상위에 올라온다.**
사람이 27곳을 고르고 설명을 쓴 것과 같아지지 않는다.

| | 사람이 쓴 홍콩 가이드 | **구운 도시 가이드** |
|---|---|---|
| 스팟 선별 | 사람이 고름 | 언어판 수 순위 + 분류 + **사람의 제외 검토**(§16.9.3) |
| 설명 | 사람이 씀(그 장소를 왜 가는지) | 위키백과 도입부 3문장(그 장소가 무엇인지) |
| 추천·팁 | 사람이 씀 | **원천에서 유도된 것만**. 없으면 미제공(§16.10) |
| 하루 테마 | 사람이 지음("도착 + 침사추이 하버뷰") | 지역명 + 대표 스팟의 **유도 라벨**(§16.13) |
| 도달 수준 | — | **근접하지만 동일해지지 않는다** |

그래서 이 설계의 목표는 "홍콩급"이 아니라 **"굽지 않은 도시의 좌표 목록보다 확실히 낫고,
그 차이를 사용자가 알 수 있다"** 이다. 등급 표시(REQ-029 · §16.17)와 README 문구가 그 "알 수
있다"를 맡는다 — **사람의 선별이 아직 낫다는 사실을 화면과 README 에서 숨기지 않는다.**
숨기면 사용자는 부족한 일정을 자기 선택 탓으로 읽는다(REQ-029 의 유저 스토리가 바로 그것이다).

### 16.2 두 시간대 분리 — DSN-31 (REQ-022 · NFR-017 · NFR-019)

위키데이터 질의 서비스(WDQS)는 중요도 순서를 안다. 그러나 **요청을 받은 자리에서 부를 수
없다** — 공개 엔드포인트 상한이 60초인데 파리가 76.0초에 504 를 냈다(실측). 가장 붐비는
관광도시에서 터지는 의존을 요청 경로에 두는 것은 설계가 아니라 사고다.

그래서 시간대를 둘로 쪼갠다. **이 저장소에 이미 있는 형태**다 — `seed/curated-places.json`
+ `services/curated.py` 가 미쉐린 목록을 그렇게 읽는다(외부 호출 없음 · TTL 없음 ·
stale 폴백 없음, §6.23).

| | **빌드 타임** (사람이 수동 실행) | **런타임** (요청 처리) |
|---|---|---|
| 사는 곳 | `tools/bake_city_guides.py` + `tools/bakery/**` | `src/harbor_lantern/**` |
| 하는 일 | WDQS · `wbgetentities` · `extracts` · Overpass 호출 → `seed/city-guides/` 로 굽기 | 구운 파일 읽기 → 순수 계산으로 일정 조립 |
| 외부 호출 | 있다 (도시당 약 10요청 · §16.18) | **0건** (NFR-017 · AC-079) |
| 캐시·TTL·stale | 없음 (파일이 결과다) | 없음 (`curated.py` 와 동일) |
| 테스트 | **실행하지 않는다**(NFR-019 · AC-081). 계산 로직은 `domain/` 에 있고 그쪽이 테스트된다 | 전량 테스트 |
| 실패 시 | 베이커가 비영 종료 + 보고서에 사유(§16.18) | 해당 도시 파일이 없으면 폴백 경로(REQ-028) |

**계층 규칙(§2.2)을 그대로 따른다.** 순수 계산 — 분류 판정·중복 접기·연결 검증·등급
판정·클러스터링·일정 조립 — 은 전부 `domain/` 에 둔다. `tools/` 에는 HTTP 배선과 파일
쓰기만 남는다. 이 분할이 NFR-019(베이커를 테스트에서 실행하지 않는다)와
"그래도 베이커의 판단을 검증해야 한다"를 동시에 만족시키는 유일한 방법이다.

> **새 코드를 `services/external/discovery.py` 에 쌓지 않는다.** 그 파일은 이미
> `domain/places.py` + `services/external/overpass.py` 와 같은 일을 두 번 한다(정찰 "구조적
> 부채" 절). 이번 변경에서 **통합하지는 않는다**(최소 변경 · 회귀 위험) — 다만 새 코드를
> 그쪽에 붙이지 않는 것으로 부채가 커지는 것은 막는다. 통합은 `IMPROVEMENTS` 로 남긴다.

### 16.3 도시 대장 — DSN-32 (REQ-022 · NFR-020 · O10 확정)

굽기의 입력은 `tools/city-registry.json` **하나**다. 베이커는 이 파일 밖의 값을 받지 않는다.

```jsonc
{
  "schema_version": 1,
  "cities": [
    { "city_id": "tokyo",        // 파일명·API 식별자. [a-z0-9-]+
      "name_ko": "도쿄", "name_local": "東京", "name_en": "Tokyo",
      "country_code": "JP", "country_ko": "일본", "country_en": "Japan",
      "native_lang": "ja",       // name_original 폴백 언어 (§16.7)
      "center": { "lat": 35.6812, "lng": 139.7671 },
      "center_note": "도쿄역 — 중심점 선택 근거를 사람이 적는다",
      "radius_m": 6000,
      "sitelink_min": 20,
      "limit": 150 }
  ]
}
```

**중심·반경·`sitelink_min` 은 사람이 정하고 고정한다.** 파리를 노트르담 기준 3km 로 조이면
**에펠탑(4.2km)이 빠진다**(실측). 성능을 이유로 반경을 줄이면 AC-068(대표 장소 포함)이
깨진다 — 그래서 **성능은 반경이 아니라 질의 형태로 산다**(§16.4).

> **함정 F13 — 하한을 재시도 손잡이로 쓰지 마라.** 정찰에서 타임아웃 시 `sitelink_min` 을
> 올려 재시도했더니 **도쿄가 하한 32로 재시도되며 10건으로 나왔다. 의도한 하한 15 로 다시
> 재니 32건 · 한국어 30건(94%)이었다**(2026-09-15 34개 도시 측정). 한 도시의 등급이
> 재시도 경로 하나 때문에 '미달'과 '완전' 사이를 오간 것이다. 하한은 성능 손잡이가 아니라
> **선별 기준**이다. 그것을 흔들면 수확량이 바뀌고, 수확량이 바뀌면 등급(REQ-029)이 바뀐다.
> 즉 **측정 대상이 측정 과정에 따라 달라진다.**
> 이번 설계에서 타임아웃 대응은 **같은 질의를 같은 파라미터로** 지수 백오프 재시도(최대 3회)
> 뿐이고, 그래도 실패하면 그 도시는 `query_failed` 로 **보고서에 남기고 수록하지 않는다.**
> 파라미터를 바꾸려면 대장 파일을 사람이 고치고 다시 굽는다(그 사실이 커밋에 남는다).

대장에는 조사 대상 **30개**를 싣는다(A11 · AC-064 의 "25개 이상"). 선정 기준은 A11 이 정한
(a) 국제 관광객 수 상위 (b) 한국인 출국 상위이며, **각 항목의 `center_note` 에 근거를 적는다.**
정찰이 이미 측정한 값이 있는 도시는 그 값을 초기값으로 쓴다(도쿄 r=6km·sl≥20, 다낭
r=15km·sl≥4, 나트랑 r=15km·sl≥4, 푸꾸옥 r=25km·sl≥3 — 실측). 나머지 도시의 중심·반경은
T7 에서 사람이 채우며 **그 과정 자체가 설계가 아니라 데이터 입력**이다.

### 16.4 수확 사슬 — DSN-33 (REQ-022 · REQ-023 · NFR-020 · O11 일부)

> **개정 v1.5 (2026-09-16).** 이 절은 원래 WDQS(SPARQL) 2단계 질의였다. T8 에서 실제로
> 굽자 도시마다 실패했고, 원인을 따라간 끝에 **WDQS 를 통째로 걷어냈다.** 근거는
> `docs/_recon.md` 의 "실측 2 — WDQS 를 걷어냈다". 아래가 대체 설계다.
> **SPARQL 은 한 줄도 남지 않았다.**

**왜 WDQS 를 버렸나.** 세 가지가 차례로 드러났다(전부 실측).

1. **WDQS 는 HTTP 200 으로 실패한다.** 서버 내부 상한을 넘기면 이미 200·헤더를 보낸 뒤라
   **부분 JSON 뒤에 Java 스택 트레이스를 이어 붙인다**(파리 62,770 bytes · 61.5초 ·
   `x-served-by: wdqs1019`). 상태코드가 200 이라 재시도 판정에 걸리지 않고, 증상은
   `JSONDecodeError: Invalid control character` 로 나온다 — **타임아웃이 JSON 오류로 위장한다.**
2. **측정이 요청량에 오염된다.** 질의를 연달아 돌리면 429 가 시작되고, 그 뒤로는 몇 분 전
   57.9초에 성공하던 질의가 65.9초 504 가 된다. 이 상태에서 잰 값으로 설계를 정하면 안 된다.
3. **식힌 뒤에도 파리는 60초를 못 지켰다** — `LIMIT` 을 150→80→60 으로 낮춰도, 클래스 필터가
   있든 없든. 즉 §16.4 의 원래 전제("클래스 조인을 빼면 싸진다")가 **틀렸다.** 클래스 필터는
   오히려 가지치기를 하고 있었고, 빼면 반경 안의 모든 좌표 항목에 sitelinks 를 붙여 정렬하게
   된다. 공개 WDQS 는 이 프로젝트가 필요한 질의량을 감당하지 못한다.

**대체 사슬은 모든 축에서 낫다.**

| | WDQS SPARQL | **ko.wikipedia geosearch (채택)** |
|---|---|---|
| 파리 1단계 | 60초 초과 · 잘림/504 | **1.0초** |
| 파리 사슬 전체 | — | **16.3초 · 9요청** (Q-id 매핑 173/173) |
| 35개 도시 조사 | 수 시간 + throttle | **41초** (도시당 1요청) |
| 한국어 | 51~92% 로 흔들림 | **100%** — 구조상(한국어 문서만 돌아온다) |
| 랭킹 근거 | `sitelinks` | `sitelinks` (동일) |
| 분류 근거 | `P31` | `P31` (동일 · 같은 요청에 실려 온다) |

(실측 2026-09-16 · `docs/_recon.md`. 랭킹 결과도 같다 — 에펠탑 191 · 루브르 169 ·
노트르담 125 · 개선문 85 · 페르라셰즈 71 · 엘리제궁 66.)

**사슬 (도시 하나당)**

| # | 호출 | 배치 | 얻는 것 |
|---|------|------|---------|
| 1 | `ko.wikipedia` `action=query&list=geosearch` | 1요청 (`gslimit` ≤ 500) | 중심 반경 안의 **한국어 문서**: `pageid`·`title`·`lat`·`lon`·`dist` |
| 2 | `ko.wikipedia` `prop=pageprops&ppprop=wikibase_item` | pageid **50개**씩 | `pageid` → **Q-id** |
| 3 | `wikidata` `wbgetentities&props=sitelinks\|claims` | Q-id **50개**씩 | `sitelinks`(랭킹) · `P31`(분류) · `P625`(좌표 대조) |
| 4 | — (네트워크 없음) | — | 파이썬 분류·접기·선별 (§16.5 · §16.6 · §16.9 그대로) |
| 5 | `ko.wikipedia` `prop=extracts` | 제목 **20개**씩 (`exintro` 필수) | 선별된 스팟의 한국어 설명 (§16.7) |
| 6 | Overpass | 1요청 | 영업시간 (§16.7) |

- **1단계는 거리순이다. 랭킹이 아니다.** geosearch 에는 유명도 개념이 없다 — 순위는 3단계의
  `sitelinks` 로 매긴다. 그래서 1단계는 **넓게 긁고**(`gslimit` 상한까지) 자르지 않는다.
  잘라야 할 이유가 없다: 1.0~1.6초짜리 요청 하나다.
- **`sitelink_min` 의 자리가 바뀐다**(§16.3). 예전에는 질의를 싸게 만드는 필터였다. 이제
  1단계에 필터가 없으므로 **랭킹 하한**으로만 남는다 — 대장에서 지우지 않고 의미를 바꿔
  기술한다. 지우면 "왜 이 도시는 잡동사니가 실렸나"를 조절할 손잡이가 없어진다.
- **분류는 여전히 파이썬이 한다**(§16.5). 원래 설계가 그렇게 정한 이유는 그대로 유효하고,
  오히려 더 잘 맞는다 — `P31` 이 3단계 응답에 실려 오므로 **분류 때문에 늘어나는 요청이 없다.**
- 같은 이유로 **잡음은 여전히 들어온다**. 파리 실측 상위에 파리 자신(366) · 유럽 우주국(118) ·
  주변 코뮌(불로뉴비양쿠르 96 · 생드니 94) · 프랑스 제3공화국(83) · 샤를리 에브도 테러(75)가
  섞여 있었다. 이것이 §16.5 분류기와 §16.9 사람 검토가 처리할 입력이다.

**한계 (반드시 `known_gaps` 에 문장으로 남긴다)**

- **한국어 문서가 없는 장소는 잡히지 않는다.** 좌표가 없는 한국어 문서도 마찬가지다.
- 그러나 이 제품은 **한국어 가이드**이고 설명도 한국어 위키백과에서 온다. 그런 장소는 원래도
  영어 이름 + 빈 설명으로 실렸을 것이다 — **제약의 방향이 제품 목표와 같다.** 그래도 사용자가
  "이 도시에 이것밖에 없나"로 읽지 않도록 데이터에 남긴다.
- geosearch 반경 상한은 10km 다. 그보다 넓게 보려면 중심을 나눠 여러 번 부른다 —
  현재 대장의 도시는 전부 10km 안이므로 쓰지 않는다(다낭 15km·푸꾸옥 25km 는 수록 제외 도시라
  해당 없음).

**실패 처리.** 준수 User-Agent 로 200요청/분이 상한이다(mediawiki.org Rate_limits · 2026-09-15).
사슬 전체가 도시당 약 9~12요청이므로 여유가 크다. 그럼에도 실패하면 그 도시는 `query_failed`
로 기록되고 수록되지 않는다 — **조용히 빠지지 않는다**(AC-084). `Retry-After` 존중과 429 의
긴 백오프는 이미 반영돼 있다(커밋 `cc8c73c`).

### 16.5 방문 가능 분류기 — DSN-34 (REQ-023 · O11 확정)

`src/harbor_lantern/domain/guide_taxonomy.py` — **순수 함수**다.

```python
def classify(direct_classes: Sequence[str],          # 직접 P31 QID 들
             ancestry: Mapping[str, Sequence[str]],  # 클래스 QID → 상위(P279) QID 들 (승급 캐시)
             ) -> Classification
# Classification: decision: Literal["accept","exclude","unclassified"]
#                 root: str | None      # 'museum' | 'monument' | ...
#                 matched_class: str | None
#                 reason: str
```

판정은 **이 순서로** 적용하고 처음 맞는 것을 채택한다.

| # | 규칙 | 결과 | 근거 |
|---|------|------|------|
| 1 | 직접 `P31` 중 하나라도 `EXCLUDE_FLAT` 에 있으면 | `exclude` | 상위를 **도시 자신**(파리 366) · **언어**(프랑스어 352) · 기관 본부 · 철도회사 · 역사적 사건이 먹는다(실측) |
| 2 | 직접 `P31` 중 하나라도 `ALLOW_FLAT` 에 있으면 | `accept` | 대부분의 항목이 여기서 끝난다 |
| 3 | 직접 `P31` 의 상위를 **P279 로 최대 3단계** 올라가 `ALLOW_ROOT` 에 닿으면 | `accept` | 허용목록의 롱테일(“불교 사원”·“미술 박물관” 같은 하위 분류)을 사람이 전부 나열할 수 없다 |
| 4 | 그 외 | `unclassified` | **버리되 보고서에 남긴다** — 다음 굽기에서 사람이 허용목록에 올릴 수 있게 |

**제외는 평면 `P31` 로만 한다 (R7 · 절대 규칙).** 하위분류까지 제외했더니 **로마에서 콜로세움이
사라졌다** — 원형경기장이 '스포츠 시설' 아래에 달려 있다(실측). 평면으로 바꾸자 돌아왔다.
비용도 마찬가지였다(오사카 45→16건, 48.7초).

**승급(규칙 3)은 왜 안전한가.** 방향이 반대다. 제외의 `P279*` 는 *위에서 아래로* 훑어
예상 못 한 자손을 삼키지만, 승급은 *아래에서 위로* 3단계만 올라가 **명시된 뿌리에 닿는지**만
본다. 닿지 못하면 `accept` 가 아니라 `unclassified` 이므로 **침묵 삭제가 아니라 기록된 보류**다.

**허용/제외 목록과 승급 캐시는 `tools/wikidata-classes.json` 에 커밋한다.**

```jsonc
{ "schema_version": 1,
  "exclude_flat":  { "Q515": "도시", "Q34770": "언어", "Q4830453": "기업", "Q178561": "전투", "Q5": "사람", "...": "..." },
  "allow_flat":    { "Q33506": "박물관", "Q570116": "관광명소", "Q16970": "교회", "...": "..." },
  "allow_root":    { "Q570116": "attraction", "Q33506": "museum", "Q1370598": "worship",
                     "Q23413": "castle", "Q22698": "park", "Q4989906": "monument",
                     "Q41176": "building_landmark", "Q12280": "bridge", "Q4022": "river" },
  "ancestry_cache": { "Q44539": ["Q16970", "Q1370598"] }   // 클래스 → 상위 (굽기 중 자동 증분)
}
```

- `ancestry_cache` 는 굽기 중 `wbgetentities` 로 채워지고 **커밋된다.** 도시가 늘수록 캐시
  적중률이 올라 요청이 줄고, 커밋된 캐시 덕분에 **같은 입력에 같은 판정**이 나온다(NFR-020).
- `allow_root` 에 **다리·강을 넣는다.** 다낭 후보 14건 중 다리 4·강 2 였다(실측) — 그곳에서는
  실제로 그것이 명소다(롱교·한강). 대신 **구성비를 수확 지표에 기록**해(§16.9) 사람이
  "명소 밀도가 낮다"를 읽을 수 있게 한다. 조용히 빼면 후보 수만 줄고 이유는 남지 않는다.
- `category`(= `root`)는 화면 라벨과 일정 규칙(저녁 슬롯·관심사 필터)의 입력이다.

### 16.6 후보 정규화 — DSN-35 (REQ-022 · AC-065)

`domain/guide_taxonomy.py` 와 같은 계층의 순수 함수(`domain/guide_harvest.py`).

```python
def fold_candidates(rows: Sequence[Mapping[str, Any]],    # 1단계 SPARQL 행들
                    center: LatLng, radius_m: float) -> tuple[Candidate, ...]
```

정찰이 잡은 **중복 두 경로**를 둘 다 막는다.

| 원인 | 증상 | 처리 |
|------|------|------|
| `P31` 타입이 여럿 | 파리가 6행(도시·수도·메트로폴리스…) | **1단계에서 `P31` 을 묻지 않으므로 애초에 생기지 않는다**(§16.4) |
| `P625` 좌표 문이 여럿 | 도쿄 스미다강 2행 · 다낭 선짜산 3행 | 항목별로 접되, **중심에 가장 가까운 좌표**를 채택. 동률이면 `(lat, lng)` 사전순 |

- **`SAMPLE()` 대신 "중심에 가장 가까운 좌표"를 쓰는 이유가 둘이다.** ① 결정론(NFR-020).
  ② 그 선택이 **반경 불변식을 자동으로 지킨다** — 채택한 좌표가 반경을 벗어나면 다른 어떤
  좌표도 벗어나므로, 접기 후 `haversine_m(center, coord) <= radius_m` 재검증이 통과한다(AC-065).
- **이름 중복**(다른 QID 인데 같은 표기)은 `sitelinks` 가 큰 쪽만 남기고 **탈락분을 보고서에
  기록**한다(AC-065 의 "중복 이름 없음"). 좌표 중복은 접지 않는다 — 같은 건물에 든 서로 다른
  명소가 사라진다(§6.23 에서 이미 배운 것).
- 정렬은 `(-sitelinks, qid)` 로 **고정**한다. 이 순서가 그대로 중요도 순위이고 AC-068 의 기준이다.

### 16.7 설명 수집 — DSN-36 (REQ-024 · NFR-018 · NFR-020 · O15 확정)

**2단계 (`wbgetentities` · 50개/요청).** 공급자가 고지한 배치 상한이 50 이다(§16.21).

```
GET https://www.wikidata.org/w/api.php
    ?action=wbgetentities&format=json&ids=Q243|Q19675|…
    &props=labels|sitelinks|claims
    &languages=ko|en|{native_lang}
    &sitefilter=kowiki|enwiki
```

한 번의 응답이 **네 가지**를 준다 — 한국어·영어·현지어 라벨, kowiki/enwiki 문서 제목,
`P31`(분류 · §16.5), `P131`(행정구역 · §16.13), `P625`(검증용 좌표 · §16.8).

**표기 폴백(O15 확정).**

| 필드 | 폴백 순서 | 규칙 |
|------|----------|------|
| `name` (한국어 이름) | ko 라벨 → en 라벨 → `native_lang` 라벨 → 아무 라벨 | **빈 문자열이 되지 않는다**(AC-069). 어떤 단계에서 왔는지 `name_source` 로 기록 |
| `name_original` (원어명) | `P1705`(원어명) → `native_lang` 라벨 → en 라벨 → `""` | 없으면 화면이 한국어 이름만 보인다 |

`ko_label_ratio` = (`name_source == "ko"` 인 스팟 수) / (수록 스팟 수). **폴백으로 채운 이름을
한국어 라벨로 세지 않는다** — 그렇게 세면 등급(AC-083)이 거짓이 된다.

**3단계 (`extracts` · 20건/요청 · 다건은 `exintro` 필수).**

```
GET https://ko.wikipedia.org/w/api.php
    ?action=query&format=json&prop=extracts|coordinates
    &exintro=1&explaintext=1&exsentences=3&exlimit=20&redirects=1
    &titles=에펠탑|루브르 박물관|…
```

- 정찰 실측에서 이 조합이 **170~260자**의 한국어 요약을 줬다 — 홍콩 가이드의 `description`
  길이와 거의 같다. 새 요약 규칙을 만들지 않는 이유가 이것이다.
- **`prop` 에 `coordinates` 를 함께 건다.** 요청은 그대로 하나인데 §16.8 의 교차검증 근거가
  공짜로 들어온다. 검증을 위해 요청을 늘리면 검증을 건너뛸 유혹이 생긴다.
- **한국어 문서가 없으면 설명은 비운다.** 영어 원문을 대신 싣지 않는다 — 한국어 앱에서
  "설명이 있다"는 표시와 실제로 읽히는 것이 어긋난다. 그 도시의 `known_gaps` 에 건수를 적는다.
- 라이선스: 본문은 **CC BY-SA 4.0** 이며 **출처 링크로 저작자 표시 요건을 만족**하는 것으로
  본다(A12 · 위키미디어 이용약관, 2026-09-15 조회). 그래서 `description` 이 있으면
  `description_source` 의 **URL · 라이선스 식별자 · 조회일 세 필드가 전부** 있어야 한다(AC-070).

**4단계 (Overpass · 도시당 1요청 · 영업시간).**

```overpassql
[out:json][timeout:60];
nwr(around:{RADIUS},{LAT},{LNG})["wikidata"];
out center tags 2000;
```

- **이름으로 맞추지 않는다. `wikidata` 태그의 QID 로 맞춘다.** 이름 매칭이 어떻게 조용히
  틀리는지는 이 저장소에 실물 기록이 있다 — 미쉐린 좌표 작업에서 `Duddell's` 가 공항 지점,
  `Amber` 가 타이항의 동명 가게로 잡혔다(§6.23). QID 는 그 실패 양식이 구조적으로 없다.
- 우리 후보 집합에 없는 QID 는 전부 버린다. 얻는 것은 `opening_hours`·`fee`·`website` 와
  OSM 요소 URL(출처)뿐이다. 좌표는 **가져오지 않는다** — 좌표의 진실은 위키데이터 쪽이고,
  두 출처를 섞으면 어느 것이 검증 대상인지 흐려진다.

### 16.8 연결 검증 — DSN-37 (REQ-030 · O17 확정 · AC-086~088)

**이 기능의 가장 위험한 실패 양식이다.** 정찰에서 식별자를 기억으로 적었다가 틀렸는데,
파이프라인은 오류를 내지 않고 매끄러운 설명을 돌려줬다 — 오사카성 자리에 **겨울 궁전**,
통천각 자리에 **댈러스 카우보이스**, 왓 프라깨오 자리에 **시온수도회**(실측).
설명이 비어 있으면 사용자는 없는 줄 알지만, **틀린 설명은 맞는 줄 안다.**

`src/harbor_lantern/domain/guide_link.py` — 순수 함수. 네트워크도 시계도 없다(AC-088).

```python

COORD_LOOSE_M = 5_000.0     # 라벨이 정확히 일치할 때까지 허용하는 거리

def verify_link(spot: LinkInput) -> LinkVerdict
# LinkVerdict: status: Literal["passed","failed"]
#              coord_delta_m: float | None
```

**방어선은 넷이다.**

1. **출처 고정.** Q-id 는 **좌표를 준 1단계 질의에서 나온 것만** 쓴다. 베이커 CLI 에 QID 인자가
   **없다** — 사람이 적은 식별자가 파이프라인에 들어갈 경로 자체를 만들지 않는다(A17).
2. **제목 정합.** `extracts` 응답의 `normalized`·`redirects` 매핑을 따라간 **최종 제목**으로
   비교한다. 리디렉트 자체는 흔하므로 실패로 보지 않되, 리디렉트가 있었다는 사실을 기록한다 —
   제목이 조용히 다른 주제로 옮겨 가는 경로가 여기다.
3. **좌표 대조.** 위키백과 문서의 `coordinates` 와 스팟 좌표의 하버사인 거리.
4. **라벨 대조.** 최종 문서 제목과 스팟의 한국어·원어·영어 이름.

**판정표 (O17 확정).** 두 근거 중 하나가 강하면 다른 하나를 완화하되, **둘 다 약하면 실패**다.
너무 조이면 맞는 설명이 사라지고, 풀면 '겨울 궁전'이 통과한다.

| 라벨 | 좌표 오차 ≤ 1,500m | ≤ 5,000m | > 5,000m | 문서에 좌표 없음 |
|------|------------------|----------|----------|-----------------|
| `exact` | passed | passed | failed | **passed** |
| `partial` | passed | failed | failed | failed |
| `none` | failed | failed | failed | failed |

- 겨울 궁전 사례 검산: 라벨 `none`(오사카성 ↔ 겨울 궁전) · 좌표 오차 약 8,000km →
  **failed** ✓ (AC-086 의 고정 입력 테스트가 이 조합을 그대로 쓴다).
- 좌표가 없는 문서라도 제목이 **정확히** 일치하면 통과시킨다. 인물·사건 문서가 그 자리에
  들어오려면 제목까지 같아야 하는데, 그건 실패 양식이 아니라 동명이의어이고 괄호 한정어
  제거 규칙이 그것을 `partial` 이하로 떨어뜨린다.

**실패하면 설명만 비운다 — 장소는 남는다**(AC-088). 그 장소는 일정에 계속 배정될 수 있고,
화면에는 "설명 미제공"이 뜬다. 목록에서 빼면 **틀린 것을 고친 것이 아니라 숨긴 것**이다.

**설명이 있는 모든 스팟은 `verification` 블록을 갖는다**(AC-087). 검증 표시 없는 설명 보유
스팟은 **0건**이어야 하며, 이 불변식은 데이터셋 테스트가 직접 센다(§16.19).

#### 16.9.2 등급 판정 — DSN-38 (AC-083 · AC-084)

`src/harbor_lantern/domain/guide_grade.py` — 순수 함수. **도시마다 재고, 미달을 조용히

```python

BELOW_MAX_SPOTS = 8;  BELOW_MAX_RATIO = 0.50
```

> **개정 v1.5 (2026-09-16) — 한국어 라벨 축이 구조적으로 무의미해졌다.**
> 수확을 ko.wikipedia `geosearch` 로 바꾸면서(§16.4) 후보가 **정의상 한국어 문서**만
> 들어온다. 따라서 `ko_label_ratio` 는 항상 1.0 이고, 아래 규칙에서 **비율 조건은 결코
> 발화하지 않는다** — 규칙 1 의 `< 0.50` 은 걸리지 않고 규칙 2 의 `>= 0.80` 은 늘 참이다.
> 실효 판정은 `spot_count` 단일 축이 된다:
> `< 8` → 미달 · `>= 15` → 완전 · 그 사이 → 부분.
>
> **그래서 코드는 고치지 않는다.** `grade(spot_count, ko_label_ratio)` 도
> `grade_city(selected)` 도 시그니처·동작 그대로 맞게 돌아간다(비율이 1.0 로 들어올 뿐이다).
> 축을 제거하려고 함수를 고치면 베네치아 사건을 고정한 회귀 테스트(후보 전체로 재면 `below`,
> 선별 후 재면 `full`)를 같이 버리게 된다 — **그 테스트는 지표를 어디서 재는가에 관한 것이라
> 수확 방식이 바뀌어도 유효하다.** 비율은 계속 기록한다: 값이 1.0 이 아닌 날이 오면
> (수확 경로가 또 바뀐 것이므로) 그 자체가 신호다.
>
> **임계값 8/15 는 재확인이 필요하다.** WDQS 후보 수로 보정한 값인데 geosearch 의 원문 수는
> 분포가 다르다(도쿄 377 · 파리 166 · 베네치아 32 · 다낭 8 · 푸꾸옥 0 — 전부 **분류 전** 수치다).
> 분류 후 수록 가능 수는 이보다 적으므로, 임계는 **T8 굽기 실측으로 확정**하고 그때
> `docs/03_개발내역서.md` 에 근거와 함께 남긴다. 판정이 바뀌는 도시가 생기면 표를 갱신한다.

판정 규칙(AC-083 문언 그대로, 적용 순서가 규칙의 일부다):

1. `spot_count < 8` **또는** `ko_label_ratio < 0.50` → **미달(below)** — 데이터셋에 수록하지 않는다.
2. 아니고 `spot_count >= 15` **그리고** `ko_label_ratio >= 0.80` → **완전(full)**.
3. 그 외 → **부분(partial)**.

#### 16.9.3 사람의 검토 단계 — DSN-50 (REQ-023 · REQ-029 · 자동 수확의 한계)

**자동 수확 결과를 그대로 내보내지 않는다.** 34개 도시 측정에서 **도쿄 1위가 '모드 학원 코쿤
타워'**(전문학교 건물)로 나왔다 — 스카이트리보다 위다. 분류로는 걸리지 않는다(`Q3918 대학`
제외로도 안 걸린다). 건축적으로 유명한 건물이라 언어판 수가 높은 것이고, **중요도 지표가
관광 중요도가 아니라는 A15 가 그대로 나타난 것**이다. 그대로 구우면 파리에서 에펠탑이
빠지는 문제를 고치고 도쿄에서 전문학교를 1위로 세운다.

그래서 굽기 흐름에 **사람이 서는 자리**를 넣는다. 자동이 못 하는 판단을 자동인 척하지 않는다.

```
uv run python tools/bake_city_guides.py --as-of 2026-09-15 --city tokyo --review
   → 상위 후보를 (순위 · 이름 · 분류 · sitelinks · 위키백과 링크) 표로 출력
   → 사람이 tools/city-denylist.json 에 제외 항목과 **근거**를 적는다
   → 같은 명령을 --review 없이 재실행 (응답 캐시 적중 · 네트워크 없음)
```

`tools/city-denylist.json` — **커밋되는 데이터**다(코드가 아니다).

```jsonc
{ "schema_version": 1,
  "cities": {
    "tokyo": [
      { "qid": "Q…", "name": "모드 학원 코쿤 타워",
        "reason": "전문학교 건물. 건축으로 언어판 수가 높을 뿐 방문 대상이 아니다. 2026-09-15 검토." }
    ]
  } }
```

| 규칙 | 이유 |
|------|------|
| `reason` 이 비어 있으면 **베이커가 실패한다** | 근거 없는 제외는 다음 사람이 되돌릴 수도 유지할 수도 없다. §16.10 이 추천·팁에 요구하는 것과 같은 규칙을 **우리 자신의 판단에도** 적용한다 |
| 제외는 **항목 단위(QID)** 다. 분류 단위 제외는 `wikidata-classes.json` 이 맡는다 | 한 도시의 잡음을 고치려고 전 도시의 분류 규칙을 흔들면 로마의 콜로세움이 사라진다(R7) |
| 제외 건수를 **데이터셋에 기록한다** (`harvest.denylisted_count`) 그리고 각 도시 `known_gaps` 에 한 줄 | 숨기면 "이 앱이 다 아는구나"로 읽힌다 — 미쉐린 목록에서 좌표 없는 항목을 숨기지 않은 것과 같은 판단 |
| 검토는 **수확과 선별 사이**에 선다 | 제외분이 상위 25(등급 평가 집합)를 차지하고 있으면 등급까지 왜곡한다 |
| 검토하지 않아도 굽기는 **동작한다** | 검토는 품질 단계이지 차단 단계가 아니다. 다만 보고서에 `reviewed: false` 가 남는다 |

**이 단계는 자동화 대상이 아니다.** "관광 대상인가"를 판정하는 규칙을 더 정교하게 만들면
로마의 콜로세움을 잃는 쪽으로 간다(실측). 사람이 25줄을 읽는 비용이 더 싸다.

### 16.10 추천·팁 유도 규칙 — DSN-39 (REQ-025 · AC-071 · AC-072)

**근거 필드가 없는 추천·팁 항목은 데이터셋에 0건이다.** 문장을 만들어 내지 않는다.

```jsonc
"tips": [
  { "text": "영업시간 09:00–23:45 (OpenStreetMap 기준 · 방문 전 확인)",
    "evidence": "opening_hours",
    "source_url": "https://www.openstreetmap.org/node/5013364" }
]
```

| `evidence` | 원천 | 이번 굽기에서 |
|-----------|------|--------------|
| `opening_hours` | OSM `opening_hours` 태그(§16.7 4단계) | **생성한다** |
| `admission` | OSM `fee`·`charge` 태그 | **생성한다** (`fee=no` → "입장 무료", `fee=yes` → "입장료 있음(금액 정보 미제공)") |
| `duration` | 없음 | **0건.** 소요시간을 주는 공개 원천을 찾지 못했다 — `known_gaps` 에 적는다 |
| `access` | 없음 | **0건.** 접근 교통을 근거 있게 유도할 원천이 이번 범위에 없다 |

- `evidence` 값은 위 네 가지로 **닫혀 있다**(AC-071). 그 밖의 값이 들어오면 데이터셋 테스트가 실패한다.
- 문장 템플릿은 **고정**이며 원천 값을 그대로 끼운다. `"꼭 방문해 보세요"` 류의 빈자리 메우기
  문구는 데이터셋·응답·화면 어디에도 없다(AC-072). 정적 검사가 금칙 문구 목록을 센다.
- 원천이 없으면 `tips: []` · `recommendations: []` 이고 화면은 **"미제공"** 을 그린다(§16.17).
  홍콩 시드가 사람이 쓴 `tip`·`recommendation` 문자열을 갖는 것과 여기가 다른 이유가 이것이다 —
  **저쪽은 사람이 쓴 편집 콘텐츠이고, 이쪽은 기계가 유도한 사실이다.** 같은 화면에 놓이더라도
  출처가 다르면 표기도 달라야 한다.

### 16.11 구운 가이드 파일 — DSN-40 (REQ-022 · REQ-024 · NFR-018 · NFR-020 · O14 확정)

**배치: 인덱스 1개 + 도시별 파일 N개** (`seed/city-guides/`).

| 파일 | 내용 | 언제 읽히나 |
|------|------|------------|
| `index.json` | 데이터셋 메타(`sources`·`known_gaps`·`retrieved_at`) + 도시 요약 목록 | 국가·도시 목록 조회(REQ-027)마다 — 작고 자주 |
| `<city_id>.json` | 그 도시의 전체 스팟과 수확 지표 | 그 도시를 고를 때만 — 크고 드물게 |
| `harvest-report.json` | **조사한 모든 도시**(미달·실패 포함)의 지표와 판정 | 런타임은 읽지 않는다. 사람과 CI 가 읽는다(AC-084) |

**O14 확정 근거.** `curated.py` 의 단일 파일 + `lru_cache(maxsize=1)` 선례를 그대로 쓰면,
도시 30개 × 스팟 수십 개 × 설명 200자가 **국가 목록 한 번 조회에 전부 메모리로 올라온다.**
분할하면 인덱스만 상주하고 도시 파일은 요청된 것만 올라온다. 분할 비용은 파일 수뿐이다.

**별도 JSON Schema 파일을 만들지 않는다.** `contracts/seed-spots.schema.json` 선례가 있지만,
`seed/curated-places.json` 은 스키마 파일 없이 **데이터셋 테스트가 계약 노릇**을 한다(§16.19).
이 확장의 불변식은 대부분 구조가 아니라 **관계**다 — "설명이 있으면 검증 표시가 있다",
"기록된 지표로 다시 계산한 등급이 기록된 등급과 같다". JSON Schema 로는 그것을 쓸 수 없다.
구조 검사까지 같은 테스트 파일에 두는 편이 계약이 한 곳에 있다.

**`<city_id>.json` — 도시 항목 (AC-063 의 "도시 항목")**

그리므로 이름이 갈리면 렌더러가 둘로 갈라진다.

```jsonc
{
  "id": "wd:Q243",                 // 가이드 식별자 (AC-066 이 이 값의 존재를 센다)
  "wikidata_id": "Q243",
  "name": "에펠탑",                 // 한국어 이름 — 빈 문자열 금지 (AC-069)

    "label_match": "exact",
```

**`sources`·`known_gaps`·`retrieved_at` 관습은 `curated-places.json` 과 동일하다**(NFR-018 ·
AC-058 의 규칙을 그대로 확장). 그래서 화면의 출처·한계 렌더러도 재사용 가능한 모양이다.

**바이트 재현성 (NFR-020 · AC-082).**

| 규칙 | 값 |
|------|-----|
| 직렬화 | `json.dumps(obj, ensure_ascii=False, sort_keys=True, indent=1)` + 끝에 `\n` 1개 |
| 개행 | `\n` 고정 (`newline="\n"` 으로 열어 Windows 에서 `\r\n` 이 섞이지 않게) |
| 좌표 | `round(x, 6)` 고정. 비율은 `round(x, 3)` |
| 조회일 | **`--as-of YYYY-MM-DD` 인자로 주입**한다. 베이커가 `date.today()` 를 읽으면 두 실행의 바이트가 달라진다 — AC-082 가 정확히 그것을 잡는다(함정 F14) |
| 순서 | 스팟은 `(-sitelinks, wikidata_id)`, 도시는 `city_id` 오름차순 |

### 16.12 런타임 로더 — DSN-41 (REQ-022 · NFR-017 · AC-063 · AC-079)

`src/harbor_lantern/services/guides.py`. **`services/curated.py` 와 같은 형태다** — 외부 호출도
TTL 도 stale 폴백도 없다. 파일을 읽어 메모리에 둔다.

```python
DATA_DIR = Path(__file__).resolve().parents[3] / "seed" / "city-guides"   # curated.py 와 같은 규칙

@dataclass(frozen=True)
class GuideIndex:
    dataset: str; retrieved_at: str; what_this_is: str
    sources: tuple[dict[str, Any], ...]; known_gaps: tuple[str, ...]
    counts: dict[str, Any]                      # surveyed / exported / full / partial / below
    cities: tuple[dict[str, Any], ...]

@dataclass(frozen=True)
class CityGuide:
    city_id: str; name_ko: str; country_code: str
    center: dict[str, float]; radius_m: int
    grade: Literal["full", "partial"]
    retrieved_at: str; harvest: dict[str, Any]
    sources: tuple[dict[str, Any], ...]; known_gaps: tuple[str, ...]
    spots: tuple[dict[str, Any], ...]

@lru_cache(maxsize=1)
def load_index(path: str | None = None) -> GuideIndex: ...

@lru_cache(maxsize=32)
def load_city(city_id: str, path: str | None = None) -> CityGuide | None: ...   # 없으면 None

def find_cities(query: str | None = None, country_code: str | None = None,
                index: GuideIndex | None = None) -> list[dict[str, Any]]: ...   # §16.15
```

- `city_id` 는 **`[a-z0-9-]+` 로 검증한 뒤에만** 경로에 붙인다. 검증 없이 붙이면 경로 조작이
  파일 읽기로 이어진다(`../`). 검증 실패는 404 이지 500 이 아니다.
- `load_city` 가 `None` 을 돌려주면 그 도시는 굽지 않은 도시이므로 **폴백 경로**(REQ-028)로 간다.
- `lru_cache(maxsize=32)` — 도시 30개 규모에서 전부 상주해도 텍스트뿐이다. 그래도 상한을 두는
  이유는 데이터가 늘었을 때 조용히 메모리를 먹지 않게 하기 위해서다.

### 16.13 하루 테마 클러스터링 — DSN-42 (REQ-026 · O12 확정 · AC-073)

`src/harbor_lantern/domain/cluster.py` — 순수 함수. 시계도 I/O 도 없다.

```python
def cluster_spots(spots: Sequence[Mapping[str, Any]], day_count: int,
                  per_day: int) -> tuple[Cluster, ...]
# Cluster: index:int, area:str, title:str, color:str, spot_ids:tuple[str,...]
```

목표 형태는 홍콩 시드다 — **하루 = 한 지역**(Day 1 "구룡(TST)", Day 2 "홍콩섬 북부"…).

1. **씨앗 선정.** 중요도 상위부터 훑으며 이미 뽑힌 씨앗과 `SEED_MIN_SEPARATION_M`(기본 1,500m)
   이상 떨어진 것을 `day_count` 개 고른다. 후보가 모자라면 가장 먼 것부터 채운다.
2. **배정.** 나머지 스팟을 **가장 가까운 씨앗**에 붙인다. 동률은 `(클러스터 index, spot id)` 로 깬다.
3. **균형 조정.** 한 클러스터가 `per_day` 를 넘으면, 그 클러스터에서 **중심에서 가장 먼**
   스팟을 여유 있는 **가장 가까운** 클러스터로 옮긴다. 옮길 곳이 없으면 그대로 둔다(잘라내지 않는다).
   반복 상한은 `spot 수` — 무한 루프가 없다는 것이 코드로 보여야 한다.
4. **지역명(`area`).** 클러스터 안에서 **최빈 `P131` 한국어 라벨**을 쓴다. 동률이면 중요도 상위
   스팟의 값. 없으면 영어 라벨, 그것도 없으면 `""`(화면은 "지역 미상"). **지어내지 않는다.**
5. **제목(`title`).** `"{area} — {대표 스팟 이름} 중심"` 고정 규칙으로 만든다. 대표는 그 클러스터의
   중요도 1위. `area` 가 비면 `"{대표 스팟 이름} 주변"`. **이것은 편집 문구가 아니라 유도 라벨이며,
   담긴 것은 전부 데이터에 있는 사실이다**(REQ-025 의 원칙을 하루 제목에도 적용한다).
6. **색(`color`).** 홍콩 시드의 팔레트(`#22d3ee`·`#f472b6`·`#fbbf24`·`#a78bfa`)를 순환한다.
   같은 화면에서 두 가이드의 색 체계가 다르면 사용자는 색에 의미가 있다고 읽는다.

**파라미터는 `config.py` 의 `GuideConfig` 한 곳에 둔다**(§6.1 과 같은 이유 — 흩어지면 "설정으로
노출한다"가 거짓말이 된다).

### 16.14 가이드 일정 생성기 — DSN-43 (REQ-023 · REQ-026 · O13 확정 · AC-066~068 · AC-073 · AC-074)

`src/harbor_lantern/domain/guide.py` — 순수 함수. **현재 시각을 읽지 않는다**(날짜는 인자다).

```python
def build_guide_plan(city: Mapping[str, Any], spots: Sequence[Mapping[str, Any]],
                     start: date, end: date, pace: str, interests: str,
                     cfg: GuideConfig) -> dict[str, Any]
```

응답 모양은 기존 `build_plan` 과 **같은 뼈대**(`days[].stops[]`·`arrival`·`departure`·
`travel_minutes`·`distance_m`·`hours_status`)를 유지한다. 화면 렌더러를 둘로 가르지 않기 위해서다.
더해지는 것은 `guide_grade`·`guide_source`·하루의 `title`·`area`·`color`·스팟의 설명/출처다.

**R8(하루 테마와 대표 장소의 충돌) 해소 순서 — AC-068 이 AC-073 보다 우선이다.**

1. **예약.** 중요도 상위 `RESERVE_TOP_N`(기본 10)개를 먼저 **반드시 들어갈 자리**로 예약한다.
   총 슬롯(일수 × 페이스)이 그보다 적으면 슬롯 수만큼 예약한다.
2. **클러스터링은 예약분 기준으로 한다**(§16.13). 나머지 스팟이 가까운 클러스터에 붙으므로,
   상위 장소가 먼저 들어가면서도 하루가 한 지역으로 묶인다.
3. **충돌 시 상위 포함이 이긴다.** 예약 스팟이 그날 지역과 다른 클러스터에 속하면 그대로 넣고,
   그 날짜에 **`area_exception: true` 와 사유 문구**를 실어 화면에 표시한다(AC-073 후단).
   조용히 버리지도, 조용히 섞지도 않는다.
4. **파리 3일 검산(AC-068)**: 예약 10개 중 에펠탑(191) · 루브르(169) · 노트르담(125)이 전부
   상위권이므로 반드시 들어간다. 일반 규칙인 "완전 등급 도시의 3일 일정에 상위 10개 중 7개
   이상"은 슬롯 15개 ≥ 예약 10개이므로 구조적으로 만족된다. **부분 등급 도시에는 적용하지
   않는다**(후보가 10개 미만일 수 있다).

**하루 창과 저녁 슬롯 (O13 확정).**

| | 가이드 경로 | 폴백 경로(기존) |
|---|---|---|
| 하루 창 | **09:00 ~ 21:00** | 09:00 ~ 19:00 (변경 없음 · A14) |
| 저녁 슬롯 | **19:00 이후 · 그날 마지막 자리** | 없음 |

- **일몰 계산을 하지 않는다.** 날짜·위도로 일몰을 근사하려면 도메인에 천문 계산이 들어오고,
  그 결과는 원천이 없는 값이다. **고정 19:00** 을 쓰고 화면에 "저녁 배치는 19:00 기준 추정"이라고
  적는다 — A8(이동시간 추정)에서 이미 쓴 방식이다.
- `evening_candidate` 는 `category ∈ {viewpoint, tower, observation}` 에서 유도한다. 후보가 있으면
  **그날의 마지막 슬롯**에 배정한다(AC-074).
- **저녁에 닫는 것으로 "확인된" 스팟만 저녁 슬롯에서 뺀다.** `hours_text` 를 기존
  `planner.opening_windows` 로 읽어 19:00 창이 닫혀 있으면 제외한다. 읽을 수 없으면(`unverified`)
  **제외하지 않는다** — 못 읽은 것을 근거로 배제하는 것은 거짓 경고를 만드는 것과 같은 실수다
  (AC-024 · R1 과 같은 원칙).
- 폴백 경로의 창을 건드리지 않는 이유: AC-078 이 "폴백의 기존 동작이 변경 전과 동일"을 요구한다.

**이동시간은 기존 식을 그대로 쓴다.** `planner.py` 안에 인라인으로 있는 계산
(≤1200m 는 `거리×1.35/80`, 그 이상은 `거리×1.45/366 + 8`)을 **순수 헬퍼 `travel_minutes(distance_m)`
로 추출**하고 `planner.build_plan` 도 그것을 호출하게 한 줄 바꾼다. 값은 바뀌지 않으므로 기존
테스트가 그대로 회귀 방어선이 된다. 두 경로가 다른 이동시간을 말하면 같은 화면에서 사용자가
그것을 본다.

**결정론 (AC-067).** 입력이 같으면 출력이 같다 — ① 시계를 읽지 않고 ② 모든 정렬에
타이브레이크(`spot id`)가 있고 ③ 집합 순회가 아니라 정렬된 시퀀스 순회다.
**여행 전체에서 같은 스팟이 두 번 배정되지 않는다**(기존 `used` 집합과 같은 규칙).

**관심사 필터(`interests`)** 는 기존 계약(`mixed|culture|nature`)을 유지하고 우리 `category` 로
매핑한다 — `culture` → `park`·`viewpoint` 제외, `nature` → `museum`·`gallery` 제외.
**예약된 상위 스팟에는 적용하지 않는다**(AC-068 이 우선한다).

### 16.15 국가·광역 입력 — DSN-44 (REQ-027 · AC-075 · AC-076)

`find_cities(query, country_code)` — **"일본"·"Japan"·"JP" 가 같은 목록을 준다.**

정규화: NFKC → 공백 제거 → casefold. 인덱스의 `country_ko`·`country_en`·`country_code` 를
같은 규칙으로 정규화해 **완전 일치**를 먼저 보고, 없으면 `name_ko`·`name_en`·`name_local` 의
접두 일치를 본다. 부분 일치를 국가명에 허용하지 않는 이유: "미국" 이 "미국령 사모아"를 끌어오는
류의 조용한 오답을 막는다.

- 결과 항목은 **그대로 일정 생성 입력**으로 쓸 수 있다 — `city_id`·`name_ko`·`center`·`grade`
  를 포함한다(AC-075).
- 구운 도시가 없는 국가는 **빈 목록 + 안내 문구를 200 으로** 반환한다(AC-076). 5xx 도 404 도
  아니다 — "없음"은 오류가 아니다. 기존 지명 검색(`/api/explore/destinations`)은 그대로 동작하며,
  화면은 두 결과를 함께 보여 준다(§16.17).

### 16.16 API 표면과 계약 변경안 — DSN-45 (REQ-022 · REQ-027 · REQ-028 · REQ-029)

**변경 원칙: 기존 경로의 응답을 깨지 않는다.** 필드는 더하기만 한다.

| 메서드 · 경로 | 인증 | 성공 | 실패 | REQ |
|--------------|------|------|------|-----|
| `GET /api/explore/guides` | 없음 | 200 (항상) | 422(쿼리 형식) | REQ-027 · REQ-022 |
| `GET /api/explore/guides/{city_id}` | 없음 | 200 | 404(굽지 않은 도시) · 422(식별자 형식) | REQ-022 · REQ-024 |

**`GET /api/explore/guides`** — 쿼리 `q`(국가·도시명, 선택) · `country`(ISO 코드, 선택).

**외부 호출 0건**이므로 `execute()`(세마포어 · 503 변환)를 타지 않는다 — 그 기계는 외부
공급자를 위한 것이고, 파일 읽기에 씌우면 "혼잡" 이라는 거짓말이 가능해진다.

**`POST /api/explore/plan` 확장**

```jsonc
// 요청 — destination 또는 city_id 중 하나는 필수 (model_validator)
{ "city_id": "paris",          // (신규 · 선택) 있으면 구운 경로
  "destination": {...},        // (기존 · 선택으로 완화) 없으면 구운 도시 중심에서 채운다
  "start_date": "...", "end_date": "...", "pace": "balanced",
  "interests": "mixed", "radius_m": 5000 }
```

```jsonc
// 응답 — 기존 필드 전부 유지 + 아래 추가
{ "guide_grade": "full",                 // full | partial | heuristic  — 항상 실린다 (AC-085)
  "guide_notice": "완전 가이드 · 조사 시점 2026-09-15",
  "guide_city": { "city_id": "paris", "name_ko": "파리", "retrieved_at": "2026-09-15",
                  "harvest": {...}, "sources": [...], "known_gaps": [...] },   // 폴백이면 null
  "days": [ { "title": "...", "area": "...", "color": "#22d3ee",
              "area_exception": false, "stops": [ { "place": { /* 설명·출처·팁 포함 */ } } ] } ] }
```

- **`guide_grade` 는 비어 있을 수 없다**(AC-085). 구운 도시면 그 도시의 등급, 아니면 `heuristic`.
  세 값의 표시 문구는 서로 다르다(§16.17).
- `city_id` 경로에서는 **`execute()` 를 타지 않는다** — 외부 호출이 0 이므로 세마포어도
  503 변환도 필요 없다. 이것이 AC-066·AC-079 를 구조적으로 보장하는 자리다.
- 폴백 경로는 코드 한 줄도 바꾸지 않는다(A14) — 기존 `build_plan` 호출을 그대로 두고
  `guide_grade: "heuristic"` 과 안내 문구만 덧붙인다(AC-077 · AC-078).

### 16.17 화면 — DSN-46 (REQ-024 · REQ-028 · REQ-029 · AC-070 · AC-077 · AC-080 · AC-085)

건드리는 것은 `web/index.html` · `web/js/explore.js`(+ 신규 `web/js/render/guide.js`) ·
`web/css/app.css` 뿐이다. **`web/hongkong.html` 과 홍콩 공유 여행 흐름은 건드리지 않는다.**

- **검색 결과가 두 줄이 된다.** 위에 **구운 도시**(등급 배지 포함), 아래에 기존 지명 검색 결과.
  "일본"을 넣으면 막다른 안내(`docs/_change_explore.md:9`) 대신 **구워 둔 일본 도시들**이 뜬다(P15).
- **등급 표시는 항상 있다**(AC-085). 세 문구가 서로 다르다:

| 등급 | 문구 |
|------|------|
| `full` | "완전 가이드 · 조사 시점 {retrieved_at}" |
| `partial` | "부분 가이드 — 자료가 적어 **일정 일부가 채워지지 않을 수 있습니다**. 조사 시점 {retrieved_at}" |
| `heuristic` | "**제한된 자동 추천** — 미리 조사한 가이드가 없는 지역입니다. 영업시간·중요도 근거가 약합니다" |

- **출처 링크는 클릭 가능한 `<a>` 여야 한다**(AC-080). 설명 아래에
  `출처: ko.wikipedia.org/… · CC BY-SA 4.0` 를 `target="_blank" rel="noopener noreferrer"` 로 그린다
  (기존 `link()` 헬퍼 재사용). 설명이 없으면 **"설명 미제공"**, 팁·추천이 없으면 **"미제공"**.
  빈자리를 문구로 메우지 않는다(AC-072).
- **`sources`·`known_gaps` 는 `<details>` 로 접어서 항상 붙인다** — 미쉐린 목록(`curatedgaps`)의
  기존 스타일과 마크업을 그대로 쓴다. 한계를 모르고 보면 이 목록을 "그 도시 전부"로 읽는다.
- **"도시 N개 지원" 같은 일괄 문구를 쓰지 않는다**(AC-064). 개수를 말할 때는 **반드시 등급별로
  쪼갠다**("완전 11 · 부분 7"). 정적 검사가 금칙 패턴(`도시 \d+개 지원` 류)을 센다.
- **사람이 쓴 가이드와 다르다는 사실을 화면과 README 가 말한다**(§16.1.1). 구운 도시의 출처
  패널에 한 줄을 고정으로 넣는다 — "이 일정은 공개 데이터에서 자동으로 구성했습니다.
  사람이 고르고 쓴 홍콩 가이드와는 선별·설명의 성격이 다릅니다." 홍콩 가이드를 이 방식으로
  재현했을 때 상위 25건 중 한국어가 12건이었고 '주룽 모스크'가 상위에 왔다(실측) — **근접하지만
  같지 않다.** 그 차이를 사용자가 알 수 있게 두는 것이 REQ-029 의 목적이다.
- 하루 카드에 `title`·`area`·`color` 를 쓴다 — 홍콩 가이드의 일자 탭과 같은 시각 언어다.
  `area_exception` 이면 그날 헤더에 "이 날은 다른 지역의 대표 장소가 포함되어 있습니다"를 붙인다.

### 16.18 베이커 CLI — DSN-47 (REQ-029 · NFR-020 · AC-082 · AC-084)

```
uv run python tools/bake_city_guides.py --as-of 2026-09-15 [--city paris] [--review] [--dry-run]
```

- **`--review`**: 굽지 않고 도시별 상위 후보를 표로 출력한다(순위·이름·분류·sitelinks·링크).
  사람이 `tools/city-denylist.json` 에 제외 항목과 **근거**를 적고 재실행한다(DSN-50 · §16.9.3).
  응답 캐시가 있으므로 재실행에 네트워크가 들지 않는다.
- **QID 인자가 없다.** 사람이 적은 식별자가 들어갈 경로를 만들지 않는다(§16.8 방어선 1).
  제외 목록의 QID 는 **수확 결과에 있는 것만** 유효하다 — 없는 QID 가 적혀 있으면 경고로 보고한다
  (오타가 조용히 아무것도 제외하지 않는 것을 막는다).
- `--as-of` 는 **필수**다. 시계를 읽지 않으므로 두 번 실행해도 바이트가 같다(AC-082 · F14).
- `--dry-run` 은 보고서만 출력하고 `seed/` 를 쓰지 않는다.
- 구조: `tools/bake_city_guides.py`(CLI) + `tools/bakery/{wdqs,wikidata,wikipedia,osm,io}.py`.
  **판단은 전부 `domain/` 을 호출한다** — `tools/` 에 있는 것은 HTTP 배선과 파일 쓰기뿐이다.

**요청 예산 (NFR-020 · 공급자 고지 준수).**

| 단계 | 요청 수 | 배치 상한 | 근거 |
|------|--------|----------|------|
| 1단계 WDQS | 1 | — | §16.4 |
| 2단계 `wbgetentities` | `ceil(후보/50)` ≤ 3 | **50** | 공급자 고지 (§16.21) |
| 승급 캐시 채우기 | `ceil(신규 클래스/50)` — 도시가 늘수록 0 에 수렴 | 50 | §16.5 |
| 3단계 `extracts` | `ceil(스팟/20)` | **20** (다건은 `exintro` 필수) | 공급자 고지 |

| **도시당 합계** | **약 10요청** | | 정찰 실측은 후보 60건에서 약 6요청이었다 |

요청 간 최소 간격 **1.1초**(`tools/resolve_curated.py` 의 선례와 같은 값), User-Agent 는

여유가 크다. 간격·배치 크기는 단위 테스트가 상수로 검증한다(AC-082 후단).

**재개 (NFR-020).** 응답 원문을 `.local/bake-cache/{city_id}/{stage}.json` 에 남긴다
(`.gitignore` 대상 — 원본 응답은 커밋하지 않는다, R9). 중단 후 재실행하면 캐시 적중분은
네트워크 없이 지나간다. 캐시는 `--as-of` 와 `query` 파라미터를 키에 포함하므로, 대장을 고치면
자동으로 무효화된다.

**보고서 (AC-084).** `seed/city-guides/harvest-report.json` 에 **조사한 모든 도시**가 남는다 —
통과·미달·질의 실패 전부.

```jsonc
{ "as_of": "2026-09-15", "surveyed": 34,
  "cities": [
    { "city_id": "tokyo",  "status": "exported", "grade": "full", "reviewed": true,
      "spot_count": 32, "ko_label_ratio": 0.94, "grade_window": 25,
      "candidate_count": 64, "candidate_ko_ratio": 0.71,
      "denylisted": [ { "name": "모드 학원 코쿤 타워", "reason": "전문학교 건물" } ],
      "composition": {...} },
    { "city_id": "nhatrang", "status": "below_threshold", "grade": "below",
      "spot_count": 5, "ko_label_ratio": 0.8, "reason": "스팟 5개 < 8" },
    { "city_id": "…", "status": "query_failed", "reason": "WDQS 3회 재시도 실패(504)" }
```

**자기검사 — 아래 중 하나라도 걸리면 비영 종료한다**(AC-084). **조용한 통과를 코드가 막는다.**

1. `index.json` 의 도시 집합 ≠ 보고서의 `exported` 집합 (미달 도시가 수록됐다)
2. 수록 도시에 대해 `grade_city(spots)` 재계산 결과 ≠ 기록된 `grade`·`spot_count`·`ko_label_ratio`
3. `city-denylist.json` 에 **`reason` 이 빈 항목**이 있다 (§16.9.3)
4. 설명을 가졌는데 `verification` 이 없는 스팟이 1건이라도 있다 (AC-087)
