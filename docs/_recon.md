### 질의 작성 시 확인된 함정 (그대로 반복하지 말 것)

1. **`P31` 타입마다 행이 중복된다** — 파리가 6행으로 나왔다(도시·수도·메트로폴리스…).
   `GROUP BY` + `MAX(?sitelinks)` 로 접는다.
2. **상위는 방문 대상이 아닌 것들이 먹는다** — 도시 자신(파리 366) · 언어(프랑스어 352) ·
   유네스코(본부가 파리라서) · 한큐 전철(회사) · 오사카 전투(사건). 부정 필터로는 부족하고
   **방문 가능한 분류의 허용목록**이 필요하다.
3. **제외에 `P279*` 를 쓰면 랜드마크가 조용히 사라진다** — '스포츠 시설'을 하위분류까지
   제외했더니 **로마에서 콜로세움이 없어졌다**(원형경기장이 그 아래에 달려 있다).
   제외는 **평면 `P31`** 로만 한다. 평면으로 바꾸자 콜로세움이 돌아왔다.
4. **제외의 `P279*` 는 비싸기까지 하다** — 오사카가 45건 → 16건으로 줄면서 48.7초가 걸렸다.
5. **중심점과 반경은 도시마다 정해야 한다** — 파리를 노트르담 기준 3km 로 조이면
   에펠탑(4.2km)이 빠진다. 도시별로 사람이 정하는 값이다.

**명소가 많은 도시에서는 홍콩급이 되고, 리조트 목적지에서는 되지 않는다.** 나트랑·푸꾸옥은
아고다 2025 한국인 인기 10위권인데 후보가 5건·2건이다 — 해변과 리조트가 목적인 곳이라
위키데이터에 걸릴 '명소'가 애초에 없다. 반경을 늘려도 채워지지 않는다(푸꾸옥은 25km 로 쟀다).

그러므로 **"도시 30개를 구웠다"를 일괄로 주장하지 않는다.** 베이커가 도시마다 수확량을 재고,
기준 미달인 도시는 **구운 목록에 넣지 않거나 부분 가이드로 표시**한다. 미쉐린 목록에서
좌표 없는 항목을 숨기지 않은 것과 같은 판단이다 — 숨기면 사용자가 "여기는 볼 게 없구나"가
아니라 "이 앱이 다 아는구나"로 잘못 읽는다.

**기대치 보정:** 기존 홍콩 가이드(사람이 씀)를 이 방식으로 재현하면 상위 25건 중 한국어

동일해지지 않는다.** 사람의 선별이 아직 낫다 — 이 사실을 README·화면에 숨기지 않는다.

남은 잡음도 있다: 도쿄 1위가 '모드 학원 코쿤 타워'(전문학교 건물)다. `Q3918 대학`
제외로는 안 걸린다. 베이커에 **사람의 검토 단계**가 필요한 이유다.

### 질의 결함 하나 더 — 좌표가 여럿인 항목이 중복된다

도쿄에서 스미다강이 2행, 다낭에서 선짜산이 **3행** 나왔다. `P625` 문(statement)이 여러 개인

(probe4 에서 잡은 `P31` 중복과는 다른 원인이다 — 같은 증상이 두 경로로 난다.)

### 실측 — 연결이 틀리면 빈칸이 아니라 '그럴듯한 거짓말'이 나온다 (설계 제약)

위 실험에서 Q-id 를 **기억으로 적었다가 틀렸다.** 파이프라인은 오류를 내지 않고
매끄러운 설명을 돌려줬다:

| 적은 것 | 실제로 돌아온 것 |
|---------|------------------|
| `Q182147` 오사카성 | **겨울 궁전**(상트페테르부르크) |
| `Q204862` 통천각 | **댈러스 카우보이스**(미식축구 팀) |
| `Q212201` 왓 프라깨오 | **시온수도회** |

이것이 이 기능의 가장 위험한 실패 양식이다. 설명이 비어 있으면 사용자는 없는 줄 알지만,
**틀린 설명은 맞는 줄 안다.** 그래서 베이커는 식별자를 신뢰하지 않고 **연결을 검증한다**:

1. Q-id 는 좌표·라벨을 준 **그 질의에서 나온 것만** 쓴다(사람이 적거나 다른 경로로 얻은 id 금지).
2. 위키데이터 항목의 좌표가 장소 좌표와 **허용오차 안**인지 확인한다.
3. 라벨이 장소 이름과 맞는지 확인한다.
4. 셋 중 하나라도 어긋나면 **설명을 비운다**(추측하지 않는다).

사용자가 고른 콘텐츠 정책("근거 있는 것만")과 같은 이유이고, 이 프로젝트가 영업시간 파서에
이미 적용한 원칙과도 같다 — 거짓 하나가 나머지 전부의 신뢰를 깎는다.

### 실측 2 — WDQS 를 걷어냈다 (2026-09-16 · 설계 변경의 근거)

굽기를 처음 실제로 돌리자 1단계 질의가 도시마다 죽었다. 원인을 따라가며 알게 된 것:

1. **WDQS 는 HTTP 200 으로 실패한다.** 서버 내부 상한을 넘기면 이미 200·헤더를 보낸
   뒤라 **부분 JSON 뒤에 Java 스택 트레이스를 이어 붙인다**(실측: 파리 62,770 bytes,
   61.5초, `x-served-by: wdqs1019`). 상태코드가 200 이라 재시도 판정에 안 걸리고,
   증상은 `JSONDecodeError: Invalid control character` 로 나온다 — **타임아웃이
   JSON 오류로 위장한다.** 그 "제어문자"는 스택 트레이스의 탭·개행이었다.
2. **내 측정이 내 요청량에 오염됐다.** 정찰 질의를 연달아 돌리자 429 가 나오기 시작했고,
   **몇 분 전 57.9초에 성공하던 도쿄 질의가 65.9초 504 로 바뀌었다.** 그 상태로 잰
   수치를 믿고 "설계 전제가 틀렸다"고 결론 낼 뻔했다. 15분 식히고 다시 재야 했다.
3. 식힌 뒤에도 파리는 `LIMIT 150`·`LIMIT 80`·`LIMIT 60` 어디서도 60초 안에 못 끝냈다
   (클래스 필터 유무와 무관). 공개 WDQS 는 **이 프로젝트가 필요한 질의량을 감당하지 못한다.**

**대안을 찾았고, 모든 축에서 낫다 — 한국어 위키백과 `list=geosearch`.**

| | WDQS SPARQL | ko.wikipedia geosearch |
|---|---|---|
| 파리 1단계 | 60초 초과 · 잘림/504 | **1.0초** (사슬 전체 16.3초 · 9요청) |
| 35개 도시 조사 | 수 시간 + throttle | **41초** (도시당 1요청) |
| 한국어 | 51~92% 로 흔들림 | **100%** (구조상 — 한국어 문서만 돌아온다) |
| 랭킹 | `sitelinks` | `sitelinks` (동일 · wbgetentities) |
| 분류 | `P31` | `P31` (동일 · 같은 요청에 실려 온다) |

사슬: `geosearch`(좌표 주변 한국어 문서) → `pageprops`(→ Q-id, 50개씩) →
`wbgetentities`(sitelinks + P31 + 좌표, 50개씩) → 파이썬 분류·랭킹 → `extracts`(설명).
**SPARQL 이 한 줄도 없다.** 파리 실측에서 Q-id 매핑 173/173 이었고 랭킹은 그대로였다
